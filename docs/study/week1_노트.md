## 3. 공부한 개념

### 3-1. 왜 3x3 행렬인가 — 동차좌표

2D인데 왜 2x2가 아니라 3x3인가. **이동(translation)을 행렬 곱으로 표현하기 위해서**다.

2x2 행렬은 원점을 원점으로만 보낸다(선형 변환). `(x,y) → (x+tx, y+ty)` 같은 이동은 아무리 해도 2x2로 못 만든다. 그래서 좌표에 `1`을 하나 더 붙여 `(x, y, 1)`로 만들고 3x3을 쓰면, 3번째 열이 이동 성분 자리가 되어 **회전·크기·이동을 전부 한 종류의 연산(행렬 곱)으로 통일**할 수 있다.

**점과 방향의 구분:**
| | 세 번째 성분 | 이동의 영향 |
|---|---|---|
| 점(Point) | `(x, y, 1)` | 받는다 |
| 방향(Vector) | `(x, y, 0)` | **안 받는다** |

`TransformPoint`와 `TransformVector`를 따로 만든 이유가 이것이다. "속도"나 "방향" 같은 값에 카메라 이동을 더하면 안 되니까.

### 3-2. 곱셈 순서 — 오른쪽이 먼저 적용된다

열벡터 규약(`p' = M·p`)에서는 **행렬을 오른쪽부터 읽는다.**

```
View = T(half) · S(zoom) · R(θ) · T(-position)
                                   ↑ 이게 제일 먼저
```
읽는 순서: 카메라 위치를 원점으로 당기고 → 회전시키고 → 확대하고 → 화면 중앙으로 옮긴다.

**핵심은 회전과 크기 변환이 항상 원점 기준**이라는 것. 그래서 돌리고 싶은 중심(카메라 위치)을 **먼저 원점으로 옮겨야** 한다. `T(-position)`이 맨 오른쪽에 있는 이유다.

**교환법칙:**
- `T·S ≠ S·T` — 이동을 먼저 하고 확대하면 이동량까지 확대된다
- `S·R = R·S` — **단, 균등 스케일일 때만.** `sx ≠ sy`면 성립하지 않는다

### 3-3. 역행렬 — 왜 이동 항이 `-t`가 아닌가

아핀 변환의 역행렬은 이렇게 생겼다:
```
M = | A  t |        M⁻¹ = | A⁻¹  -A⁻¹t |
    | 0  1 |              |  0      1  |
```

이동 항이 그냥 `-t`가 아니라 **`-A⁻¹t`** 다. 순서를 되짚어보면 당연하다 — 원래 변환은 "회전·확대를 한 다음 이동"이므로, 되돌릴 때는 "이동을 먼저 빼고 그다음 회전·확대를 되돌려야" 한다. 그 과정에서 이동 벡터도 `A⁻¹`를 통과한다.

> ⚠️ **`zoom = 1`에서는 이 실수가 안 보인다.** `A⁻¹ = I`라서 `-A⁻¹t = -t`가 되어버리기 때문. 그래서 역행렬 검증은 반드시 `zoom ≠ 1`, `rotation ≠ 0`인 값으로 해야 한다.

**구현한 역행렬 3종:**
1. `Inverse()` — 아핀 전용. 2행이 `[0 0 1]`이라 가정하고 위 공식을 직접 사용. **실제로 쓰는 것.**
2. `InverseAdjugate()` — 여인수 전개 + 수반행렬. 학습·검산용
3. `InverseGaussJordan()` — 가우스 소거법. 학습·검산용

셋의 결과가 일치하는지 확인하면 "왜 아핀 전용이면 충분한가"를 스스로 증명한 셈이 된다. (뷰 행렬은 항상 아핀이므로 일반 3x3 역행렬의 비용을 낼 이유가 없다)

### 3-4. 좌표 공간 3단

```
World  ──[View]──▶  Screen(480x800 고정)  ──[레터박스]──▶  Window(실제 창)
       ◀─[invView]─                       ◀─[/ratio]─
```

마우스 좌표는 **Window 좌표**로 들어오므로 거꾸로 두 번 변환해야 한다:
```cpp
Vector2 Camera::WorldToMousePos(Vector2 mousePos)
{
    return ScreenToWorld(mousePos / GAME.GetRectRatio());   // 레터박스 → 뷰 역변환
}
```
레터박스 환산을 빼먹으면 **창을 최대화했을 때만 클릭이 어긋난다.** 창이 원래 크기면 `ratio = 1`이라 정상으로 보여서 못 잡는 버그.

### 3-5. 로그 줌 보간 — 왜 선형이면 안 되는가

줌 범위가 `0.005` ~ `4.0`으로 **800배**다. 선형 보간하면 중간(t=0.5)이 `2.0` — 거의 안 움직인 것처럼 보이고 마지막에 확 줄어든다. 줌은 **곱셈 공간**의 값이기 때문이다(2배 확대의 반대는 -2가 아니라 1/2).

```cpp
float a = std::exp(-k * deltaTime);          // 프레임 독립 지수감쇠
_zoom *= std::pow(_targetZoom / _zoom, 1.f - a);   // 비율을 보간
```

`exp(-k·dt)`를 쓰면 **프레임레이트와 무관하게** 같은 시간에 같은 지점에 도달한다. 단순히 `_zoom += (target - _zoom) * 0.1f` 같은 식은 프레임이 빠를수록 빨리 수렴해버린다.

수렴 시간은 대략 `3/k`초:

| `k` | 수렴 시간(95%) |
|---|---|
| 10 | 0.3초 |
| **5** (채택) | 0.6초 |
| 2 | 1.5초 |

### 3-6. `atan2` — 방향에서 각도 뽑기

`atan(y/x)`는 나눗셈하는 순간 **사분면 정보를 잃는다.** `(1,1)`과 `(-1,-1)`은 `y/x`가 둘 다 `1`이라 구분이 안 되고, `x=0`이면 아예 나눗셈이 안 된다. `atan2(y, x)`는 y와 x의 부호를 따로 보므로 네 사분면을 전부 구분한다.

**방향에서 각도를 뽑을 땐 항상 `atan2`.**

### 3-7. 각도 보간과 최단경로

`350° → 10°`를 순진하게 보간하면 `-340°`, 즉 한 바퀴를 거꾸로 돈다. 각도는 **원 위에 사는 값**이라 덧셈 공간처럼 다루면 안 된다.

```cpp
float LerpAngle(float from, float to, float t)
{
    float delta = to - from;
    delta = atan2f(sinf(delta), cosf(delta));   // ±π 안으로 자동으로 접힘
    return from + delta * t;
}
```
`sin`/`cos`를 거치면 주기성이 반영되어 자동으로 접힌다.

> ⚠️ **이 코드베이스 고유의 함정:** `Util.cpp`의 `DegreeToRadian`/`RadianToDegree`는 결과를 `[0, 2π)`로 정규화한다. **각도 "차이"를 이 함수에 통과시키면 음수가 양수로 바뀌어 최단경로 정보가 파괴된다.** 편의 함수를 재사용하는 건 좋은 습관이지만, 그 함수가 무슨 짓을 하는지 확인하고 쓰는 게 더 중요하다.

### 3-8. ⭐ 왜 행렬을 그냥 섞으면 안 되는가

두 카메라 상태 사이를 부드럽게 잇고 싶을 때, 가장 순진한 방법은 두 뷰 행렬의 성분을 하나씩 선형 보간하는 것이다. **회전이 없으면 잘 되는데, 회전이 들어오면 깨진다.**

```
R(0°) = | 1  0 |     R(180°) = | -1   0 |     성분별 평균 = | 0  0 |  ← 영행렬!
        | 0  1 |               |  0  -1 |                   | 0  0 |
```
**모든 점이 한 점으로 뭉개져 화면이 사라진다.**

90° 차이면 각 열의 길이가 `√(0.5² + 0.5²) ≈ 0.707`이 되어 **화면이 30% 쪼그라들었다 돌아온다.**

**왜 그런가:** 회전 성분 `(cosθ, sinθ)`는 **단위원 위의 점**이다. 단위원 위의 두 점을 직선으로 이으면 원 안쪽을 지난다(현이 호보다 짧으니까). 원 안쪽 = 길이 1 미만 = 스케일 축소. 180° 차이면 두 점이 정반대라 직선의 중간이 정확히 원의 중심(0)이 된다.

**올바른 방법 — 재료를 각각 보간한 뒤 재조립:**

| 파라미터 | 보간 방식 | 사는 공간 |
|---|---|---|
| 위치 | 선형 | 덧셈 |
| 각도 | `LerpAngle` 최단경로 | 원 위 |
| 줌 | 로그 | 곱셈 |

**핵심은 세 파라미터가 각각 다른 공간에 산다는 것.** 행렬 성분으로 뭉뚱그려 섞으면 세 공간의 구조가 전부 무시된다. 로그 줌(3-5)과 각도 최단경로(3-7)에서 따로 배운 것이 여기서 하나로 합쳐진다.

### 3-9. 변환 합성 — 행렬을 쓰는 두 번째 이득

우주선처럼 **자기 각도로 회전하는** 물체를 그릴 때:
```
M = View · T(우주선위치) · R(우주선각도)
로컬 삼각형 (0,-10), (-6,8), (6,8) → M.TransformPoint() → Polygon()
```

오른쪽부터: 기체를 자기 각도로 돌리고 → 월드 위치로 옮기고 → 뷰 변환.

**여기서 카메라 회전이 공짜로 따라온다.** 우주선의 화면상 각도를 "기체 각도 + 카메라 각도"로 직접 계산할 필요가 없다. 행렬 합성이 알아서 처리한다.

(첫 번째 이득은 뷰 행렬을 프레임당 한 번만 만들어 모든 객체가 재사용하는 것)

### 3-10. y축이 아래로 증가한다 (GDI)

- **"위"는 `(0, -1)`이다.** `AActor::_forwardDir` 기본값이 그렇게 되어 있다
- 수학 관례의 반시계 회전이 **화면에서는 시계 방향으로 보인다**
- 각도 부호가 헷갈리면 기존 `AActor::SetRotation` 관례를 단일 소스로 삼는다

### 3-11. 화면상 크기로 판단하기 (LOD의 원리)

행성을 어떻게 그릴지는 **월드 반지름이 아니라 화면상 반지름**으로 정해야 한다.
```cpp
float r = cam.WorldToScreenScale(_bodyRadius);   // = worldLen * _zoom
```
카메라 줌이 바뀌면 같은 행성이 다른 크기로 보이므로, **거리와 줌을 하나의 값으로 합쳐서 판단**하는 것이다. 화면에서 1px도 안 되는 것을 정밀하게 계산할 이유가 없다.

### 4-2. 기존 엔진에서 바꾼 것

- **`Camera`를 `World` 베이스로 승격** — 원래 `Camera`는 선언만 있고 아무도 안 쓰는 고아 클래스였다. `World`가 소유하고 `Enter()`에서 `Init`, `Update()`에서 `Update`하도록 배선. `AActor::_ownerWorld`가 `World*` 타입이라, 액터가 `_ownerWorld->GetCamera()`로 카메라에 접근하려면 베이스에 있어야 했다.
- **`World::PickActor()` 추가** — 원형 콜라이더 기준 히트테스트. 클릭 피킹과 카메라 팔로우 타겟 선택에 공용으로 쓴다.
- **`InputManager`에 휠 델타** — `WM_MOUSEWHEEL` → `SetWheelDelta()`, 프레임 끝에서 `ResetWheelDelta()`. 이벤트성 값이라 안 지우면 한 번 굴렸는데 계속 줌이 들어간다.
- **`Vector2` 보강** — `Normalized()`(사본 반환), 연산자 `const`화.

### 4-3. 카메라 설계 — 왜 액터마다 카메라를 두지 않았나

"우주선을 클릭하면 우주선 시점으로 전환"을 만들 때, 액터마다 `Camera` 객체를 갖게 하는 방법도 있었다. **채택하지 않았다.**

이유: 카메라가 여러 개면 전환할 때 두 객체의 `zoom`/`rotation`/`position` 상태를 서로 동기화해야 부드러운 전환이 나온다. 결국 "하나의 카메라가 목표를 바꿔가며 보간"하는 것과 똑같은 일을 하는데, 객체 수만큼 동기화 로직이 늘어난다.

**채택한 구조:** `World`가 `Camera` 하나만 소유하고, `Camera`가 `AActor* _followTarget`(nullable)을 가진다.
- `nullptr` → 자유 모드(드래그·줌으로 조작)
- 액터를 가리키면 → 그 액터 위치를 목표로 매 프레임 보간

클릭 한 번으로 `_followTarget`만 바꾸면 전환이 되고, 우주선이 생기면 그대로 꽂으면 된다.

### 4-4. 렌더 방식 — 스프라이트가 아니라 GDI 도형

`USpriteComponent`는 카메라 변환이 들어갈 자리가 없어서 우주 액터에는 쓰지 않기로 했다. `APlanet`/`ASpaceship`이 `Render()`를 직접 오버라이드해서 카메라로 좌표를 변환한 뒤 그린다.

**단, `Texture::Render()`가 `destSize` 인자로 스케일링을 지원한다는 걸 뒤늦게 발견**해서(설계 문서엔 불가능하다고 적혀 있었다), 행성은 GDI 원 대신 텍스처를 화면 크기에 맞춰 늘려 그리는 방식으로 바꿨다. 기존 씬(Title/Main/GameOver/Editor)의 렌더 경로는 전혀 건드리지 않아 회귀 위험 0.

| 줌 보간 `k` | `5.0` | `3/k ≈ 0.6초` 수렴. 체감상 자연스러움 |
| 팔로우 `_followK` | `5.0` | 위와 동일. 별도 상수로 분리해서 줌과 독립 조절 |
| 휠 한 칸당 | `0.15` (15%) | 더 크면 뚝뚝 끊긴다 |
| 최소 줌 | `0.005` | 태양계 전체가 화면에 들어오는 한계 |

### 태양계 (`MainWorld`)
| 천체 | 공전반지름 | 각속도(rad/s) | 반지름 |
|---|---|---|---|
| 태양 | — | — | 12,000 |
| 수성 | 20,000 | 0.032 | 400 |
| 금성 | 40,000 | 0.024 | 950 |
| **지구** | 60,000 | 0.020 | 1,000 |
| 화성 | 80,000 | 0.016 | 550 |
| 목성 | 120,000 | 0.009 | 4,000 |
| 토성 | 160,000 | 0.007 | 3,200 |
| 천왕성 | 200,000 | 0.005 | 2,200 |
| 해왕성 | 240,000 | 0.004 | 2,000 |

- 지구를 기준(`60,000` / `0.02` / `1,000`)으로 잡고 나머지를 상대 비율로 배치
- 바깥 행성일수록 각속도를 낮춰 공전 주기 차이를 표현
- 초기 각도는 랜덤 — 전부 일직선으로 시작하면 부자연스러움
- 시작 줌 `0.01`, 별밭 `20,000`개 / `±500,000`

### 발사 씬 (`LaunchWorld`)
| 값 | 채택값 | 근거 |
|---|---|---|
| 시작 줌 | `4.0` | 화면 세로 800px에 월드 200단위 → 우주선이 32px로 보임 |
| 우주선 도형 | `(0,-10) (-6,8) (6,8)` | 코가 `-y`(화면 위) 방향 |
| 우주선 회전 속도 | `90°/s` | 조작감 확인용 임시값 |
| 지면 | 월드 `y = 0` | 위쪽이 `-y`인 좌표 규칙과 일치 |

> 📌 원래 로드맵의 시작 파라미터 표는 "800px 정사각 화면" 가정이었는데, 실제 해상도가 `480x800`(세로형)이라 그대로 쓰면 안 맞았다. **비율 감각(우주선의 100배, 태양이 지구의 5배)은 유지하되 절대값은 직접 만져가며 조정**했다.

## 6. 로드맵에서 바뀐 것

| 항목 | 원래 계획 | 실제 | 이유 |
|---|---|---|---|
| 씬 구조 | `SpaceWorld` 하나 | `LaunchWorld` + `MainWorld` **분리** | 발사 구간과 태양계는 스케일·연출이 완전히 다름 |
| **표면 정렬(B-8)** | 필수 구현 | **폐기** | 발사대가 평면 바닥이라 보정할 기울기가 없음 |
| LOD | `30px`/`3px` 3단계 이산 | 텍스처 **연속 스케일링** | 텍스처 적용하면서 자연히 대체됨. 시각적 결과는 동등 |
| 카메라 모드 | `Fixed`/`Follow` 2종 토글 | `_followTarget` 포인터로 **일반화** | 임의의 액터를 클릭해 추적 가능 |

가장 큰 변경은 **표면 정렬 폐기**다. 설계 문서가 "둥근 행성 표면에서 발사"를 전제로 쓰였기 때문에 필수 항목으로 잡혀 있었는데, 실제 게임 흐름(평면 바닥에서 발사 → 화면 전환 → 태양계)을 정리하고 나니 전제가 성립하지 않았다. **전제가 바뀌면 그 위에 세워진 항목도 다시 검토해야 한다**는 걸 코드를 절반쯤 만든 뒤에 깨달았다. (상세: `1주차_troubleShooting.md` 18번)

## 8. 2주차로 넘어가며

1주차에서 만든 것 중 2주차에 바로 쓰이는 것들:

- **`ASpaceship`의 변환 합성** — 방향키로 기체를 기울이면(`A`/`D`) 도형이 그 각도로 그려진다. 추력 방향은 `GetForwardDir()`로 바로 나온다
- **`LaunchWorld`** — 발사 시퀀스가 들어갈 그릇
- **줌 보간** — 고도에 따라 카메라가 자동으로 축소되는 연출에 재사용
- **`_followTarget`** — 우주선을 타겟으로 지정하면 추적 카메라가 된다
- **`StarField`** — 고도에 따라 별이 서서히 나타나는 대기권 연출에 재사용

2주차의 핵심은 **수치 적분기 3종(명시적 오일러 / 반암시적 오일러 / RK4) 비교**다. 물리 상수는 2주차 가이드에서 받는다.
