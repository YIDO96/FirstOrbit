3주차는 1~2주차보다 훨씬 가볍다. 이유는 **발사까지 전부 이미 완성**되어 있기 때문이다.

|---|---|
| `LaunchWorld` — 발사 시퀀스 전체 | ✅ `LaunchGameMode`(`Idle→Countdown→Ascent→Failed`), `Reset()`, 지면 충돌 |

# Day 2 — 궤도 요소 계산 (근지점·원지점·이심률) ⭐

> **목표:** 현재 위치·속도만으로 "이 궤도가 어떤 모양인지" 매 프레임 계산한다.
> **이번 주차의 진짜 수학이 여기 있다.** `3주차_학습가이드.md`가 아직 없어서
> 이번 Day엔 예외적으로 유도 과정까지 이 문서에 담는다.

### 📖 왜 이 공식인가 (유도) — 시작 전에 한 번 읽을 것

두 가지 **보존량**에서 전부 나온다. 우주선에 작용하는 힘은 항상 행성 중심을 향하므로
(중심력) 아래 둘은 궤도를 도는 내내 **절대 안 변한다** — 이게 이번 Day의 검증 기준이 되는 이유다.

**① 비에너지(specific orbital energy)** — 단위 질량당 역학적 에너지
```
ε = v²/2 - μ/r
```
운동에너지(`v²/2`)와 위치에너지(`-μ/r`)의 합. 이미 2주차 `UPhysicsComponent::OnGUI()`에
있는 `E` 계산과 **완전히 같은 식**이다 — 새로 배우는 게 아니라 이름이 `eps`로 바뀔 뿐.

**② 비각운동량(specific angular momentum)** — 2D에서는 스칼라
```
h = r × v = r.x*v.y - r.y*v.x     (Vector2::Cross가 이미 이 식이다)
```
행성이 우주선을 당기는 힘은 항상 `r` 방향(중심 방향)이라 **토크가 0** → 각운동량 보존.
근지점(가까울 때)에서 빠르고 원지점(멀 때)에서 느린 이유가 바로 이 보존 법칙이다.

**③ 장반경(semi-major axis)** — 타원 궤도(`ε<0`)에서 에너지와 장반경은 1:1 대응
```
a = -μ / (2ε)
```
> 왜 부호가 이런가: 묶인 궤도(타원)는 `ε<0`(에너지가 음수 = 탈출 못 함)이어야 하고,
> `a`는 항상 양수여야 하니 분모·분자에 마이너스가 하나씩 필요하다.

**④ 이심률(eccentricity)** — "얼마나 찌그러졌는가", 0=원, 0~1=타원, 1=포물선, >1=쌍곡선
```
e = √(1 + 2εh²/μ²)
```
> 유도 스케치: 궤도 방정식 `r = p/(1+e·cosθ)`에서 반통경(semi-latus rectum) `p = h²/μ`가
> 나오고, `p = a(1-e²)`라는 기하 관계와 위 `a` 식을 합치면 이 식이 떨어진다. 자세한 전개는
> `Fundamentals of Astrodynamics`(`docs/study/`에 이미 있는 PDF) 1장 참고.

**⑤ 근지점/원지점**
```
perigee = a(1-e)      apogee = a(1+e)
```
원(`e=0`)이면 `perigee = apogee = a`. 이게 Day 2-3의 원궤도 검증이 성립하는 이유다.

### 체크리스트

- [ ] **2-1. 비에너지·각운동량** `~20분`
  ```cpp
  Vector2 r = _ship->GetCenterPos() - _home->GetCenterPos();
  Vector2 v = _ship->GetComponent<UPhysicsComponent>()->GetVelocity();
  float mu = _home->GetMu();

  float eps = 0.5f * v.LengthSquared() - mu / r.Length();   // 비에너지 — UPhysicsComponent::OnGUI()의 E와 동일
  float h   = r.Cross(v);                                    // 각운동량 (2D는 스칼라)
  ```
  - `eps`는 이미 2주차부터 ImGui에 찍어오던 값이다 — 새로 만드는 게 아니라 **재사용**
  - `Vector2::Cross`는 `Structs.h`에 `x*other.y - y*other.x`로 이미 정의돼 있다 (직접 구현할 필요 없음)
  - ⚠️ `h`의 부호는 공전 방향(시계/반시계)에 따라 +/- 둘 다 나올 수 있다 — **정상이다.**
    아래 `e` 공식이 `h²`(제곱)만 쓰므로 부호는 결과에 영향 없다

- [ ] **⭐ 2-2. 이심률·장반경 → 근지점/원지점** `~30분`
  ```cpp
  float a = -mu / (2.f * eps);                          // 장반경 (eps<0일 때만 의미 있음)
  float e = sqrtf(max(0.f, 1.f + 2.f * eps * h * h / (mu * mu)));
  float perigee = a * (1.f - e);
  float apogee  = a * (1.f + e);
  ```
  - ⚠️ **`eps >= 0`이면 반드시 먼저 걸러낼 것.** `a = -mu/(2*eps)`에서 `eps`가 0에 가까울수록
    `a`가 무한대로 발산한다(포물선 궤도의 정의가 정확히 이거다). `eps`가 정확히 0이면
    나눗셈 자체가 `inf`/`NaN`이 된다. **`if (eps < 0)`으로 먼저 분기하고, 그 분기 밖에서는
    근지점/원지점을 아예 계산하지 않는다** (탈출 궤도는 근지점/원지점 개념이 없다)
  - ⚠️ **부동소수점 팁:** `eps`는 `v²/2`와 `μ/r`이라는 **비슷한 크기의 두 값을 빼서** 나온다.
    원궤도에 아주 가까울수록(또는 탈출 속도에 아주 가까울수록) 두 값이 서로를 거의 상쇄해서
    `eps`가 작은 값이 되고, 상대오차가 커질 수 있다(자릿수 손실, catastrophic cancellation).
    지금 스케일(`μ=2e7`, `v²`~15000대)에선 문제될 정도는 아니지만, **왜 1주차부터 `float`
    정밀도를 신경 써왔는지**와 같은 맥락이라는 것만 기억해두면 된다

## 4. 막혔을 때 — 범위 좁히기

3주차 버그는 대부분 "이미 맞는 값(2주차)을 3주차 공식이 잘못 읽는" 형태다.

```
0. 근지점/원지점이 이상값(NaN, 음의 무한대)인가?
   → eps >= 0(탈출) 케이스를 안 걸러내고 a=-mu/(2*eps)를 그대로 계산한 것
1. 완전한 원궤도(KEY_0)에서도 근지점≠원지점인가?
   → r, v를 GetCenterPos()/GetVelocity()가 아니라 다른 값을 읽고 있는지 확인
   → Cross()가 2D에서 스칼라를 반환하는 게 맞는지(Vector2::Cross 구현 확인)
2. 승리 판정이 한 번도 안 뜨는가?
   → 기준을 bodyRadius로 했는지 kAtmosphereHeight로 했는지(3-1) 다시 확인
   → eps < 0인데도 계산에서 escaped로 잘못 분기되고 있는지
3. LaunchWorld에서 MainWorld로 넘어온 직후 값이 이상한가?
   → 2주차 6-2의 핸드오프 좌표 변환(발사대 위치 → 홈 행성 표면 기준)을 의심
   → GAME.ConsumeLaunchHandoff가 두 번째 진입에서도 옛날 값을 재사용하고 있는지
     (consume 패턴이 제대로 플래그를 껐는지)
4. 예측선(Day 4)이 실제 궤적과 어긋나는가?
   → 예측에 쓴 적분기가 본체(UPhysicsComponent)와 다른지 확인
```

> 🔑 **3주차는 새 버그보다 "2주차 값을 잘못 해석"하는 버그가 훨씬 많다.**
> 의심 순서: 먼저 **2주차에서 이미 검증된 값(r, v, μ)을 제대로 읽고 있는지**부터 확인하고,
> 그다음에 3주차 공식(근지점/원지점) 자체를 의심한다.
