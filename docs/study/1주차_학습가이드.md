# Part A. 공부 내용

## A-1. 왜 3x3인가 — 동차좌표(Homogeneous Coordinates)

### 문제 상황

2D 변환 세 가지를 그냥 쓰면 이렇게 된다.

```
스케일:  x' = s·x           → 곱셈
회전:    x' = x·cosθ - y·sinθ → 곱셈
이동:    x' = x + tx        → 덧셈  ← 얘만 혼자 다르다
```

스케일과 회전은 2x2 행렬 하나로 표현되는데, **이동만 행렬 곱으로 표현이 안 된다.**

```
| a b | | x |   | ax + by |
| c d | | y | = | cx + dy |     ← 상수항(+tx)을 만들 자리가 없다
```

2x2 행렬은 **원점을 절대 옮기지 못한다.** `(0,0)`을 넣으면 무조건 `(0,0)`이 나온다.
그래서 "스케일 → 회전 → 이동"을 하려면 `곱 → 곱 → 합`을 따로 관리해야 하고,
변환을 여러 개 합칠 때마다 순서를 손으로 챙겨야 한다.

### 해결 — 차원을 하나 늘린다

좌표에 **1을 하나 붙여서** `(x, y, 1)`로 만들고, 행렬을 3x3으로 키운다.

```
| 1  0  tx | | x |   | x + tx·1 |   | x + tx |
| 0  1  ty | | y | = | y + ty·1 | = | y + ty |
| 0  0  1  | | 1 |   |     1    |   |    1   |
```

**세 번째 성분의 `1`이 `tx`를 끌어내리는 스위치 역할을 한다.**
`tx`는 `1`과 곱해져서 살아남고, 결과의 세 번째 성분은 다시 `1`이라 계속 이어붙일 수 있다.

> 💡 이게 동차좌표의 전부다. "이동을 곱셈으로 만들기 위해 차원을 하나 빌린다."

### 점(point)과 방향(vector)의 차이

세 번째 성분에 `0`을 넣으면 어떻게 될까?

```
| 1  0  tx | | x |   | x + tx·0 |   | x |
| 0  1  ty | | y | = | y + ty·0 | = | y |     ← 이동이 무시된다
| 0  0  1  | | 0 |   |     0    |   | 0 |
```

- **점 `(x, y, 1)`** — 위치. 이동의 영향을 받는다.
- **방향 `(x, y, 0)`** — 화살표. 이동의 영향을 받지 않는다.

**왜 이게 맞는가:** "서울에서 부산 방향"이라는 벡터는 내가 어디로 이동하든 그대로다.
방향에는 위치 개념이 없으므로 평행이동이 적용되면 안 된다.
반면 스케일과 회전은 방향에도 적용되어야 한다 (`0`을 넣어도 좌상단 2x2는 그대로 작동한다).

> 📌 그래서 `TransformPoint`(1을 넣음)와 `TransformVector`(0을 넣음)를 **따로** 만든다.
> 속도 벡터를 실수로 `TransformPoint`에 넣으면 카메라 위치만큼 엉뚱하게 밀린다.

## A-2. 변환 행렬 3종의 생김새

각 행렬이 "왜 저렇게 생겼는지"는 **단위벡터가 어디로 가는지**를 보면 이해된다.
행렬의 **1열은 `(1,0)`이 가는 곳**, **2열은 `(0,1)`이 가는 곳**, **3열은 원점이 가는 곳**이다.

### 이동 T(t)
```
| 1  0  tx |
| 0  1  ty |     (1,0)→(1,0),  (0,1)→(0,1),  원점→(tx,ty)
| 0  0  1  |     축은 그대로, 원점만 옮긴다
```

### 스케일 S(s)
```
| s  0  0 |
| 0  s  0 |      (1,0)→(s,0),  (0,1)→(0,s),  원점→원점
| 0  0  1 |      축이 s배로 늘어난다
```

### 회전 R(θ)
```
| cosθ  -sinθ  0 |
| sinθ   cosθ  0 |    (1,0)→(cosθ, sinθ),  (0,1)→(-sinθ, cosθ)
|  0      0    1 |
```

### 회전이 이 프로젝트에서 하는 일 (⭐)

카메라 회전은 장식이 아니라 **기획의 핵심 연출을 성립시키는 필수 요소**다.

기획서 7.1은 이렇게 말한다 — *"지표면에선 행성 곡률이 지평선처럼 보여 횡스크롤로 느껴진다."*
그런데 우리 행성은 **원**이다. 발사대가 행성의 어느 지점에 있느냐에 따라
"지면"의 방향이 매번 다르다.

```
        회전 없음                        회전 있음
   ┌──────────────┐               ┌──────────────┐
   │      ／      │               │              │
   │    ／  🚀    │               │      🚀      │
   │  ／          │               │              │
   │ ●행성        │               │──────────────│  ← 지평선이 수평
   └──────────────┘               └──────────────┘
   옆구리에서 발사하면            카메라가 로컬 "위"에
   화면이 누워 보인다             정렬돼 항상 똑바로
```

**카메라를 그 지점의 로컬 "위"(행성 중심 → 발사대 방향)에 정렬시켜야
비로소 지평선이 수평이 되고 횡스크롤처럼 느껴진다.** (구하는 법은 A-8)

그리고 상승하면서 이 정렬이 **서서히 풀린다**. 대기권을 벗어나면 정렬 0(월드 기준)이
되어 궤도를 위에서 본 탑뷰가 된다. 즉:

> **고도 하나가 `줌 · 하늘색 · 별 밝기 · 회전` 네 가지를 동시에 구동한다.**

기획서 7.1의 *"별도 화면 교체가 아니라 하나의 뷰 행렬이 연속 변화하는 것"* 이
코드에서는 이 문장 하나로 떨어진다.

> ⚠️ **이 프로젝트의 좌표계 함정 (A-7 참고)** — GDI는 y축이 아래로 증가한다.
> 위 회전 행렬은 수학 관례(y가 위로)의 **반시계 방향**인데, y-down 화면에서는
> **시계 방향으로 보인다.** 기존 `AActor::SetRotation`이 이미 이 관례로 짜여 있으니
> (`_forwardDir = Vector2(0,-1).Rotate(rad)`) 거기에 맞추면 된다.

## A-3. 행렬 곱 — 그리고 순서가 왜 중요한가

### 곱의 정의

```
C = A · B  일 때   C[i][j] = Σ(k=0..2)  A[i][k] · B[k][j]
```

말로 하면 **"C의 i행 j열 = A의 i행 · B의 j열"** (행 하나와 열 하나의 내적).

### 어느 쪽이 먼저 적용되는가 — 이게 핵심

우리는 **열벡터 규약**을 쓴다. `p' = M · p`.

```
p' = A · B · C · p
             └───┘  C가 p에 먼저 닿는다
         └───────┘  그다음 B
     └───────────┘  마지막에 A
```

**오른쪽에 있는 것이 먼저 적용된다.** 읽을 때는 왼쪽부터인데 적용은 오른쪽부터라
직관과 반대다. 이게 행렬 순서 버그의 근원이다.

### 우리 뷰 행렬의 의미

```cpp
_view = T(half) * S(zoom) * R(theta) * T(-position);
```

오른쪽부터 읽으면:
1. `T(-position)` — **카메라를 원점으로 끌어온다** (월드를 카메라 기준 상대좌표로)
2. `R(θ)` — **원점 기준으로 회전** (카메라가 원점에 와 있으므로 카메라 중심 회전이 됨)
3. `S(zoom)` — **원점 기준으로 확대/축소**
4. `T(half)` — **화면 중앙으로 옮긴다**

"카메라를 원점에 놓고 → 돌리고 → 줌 걸고 → 화면 중앙으로" — 이 네 문장이 그대로 코드다.

> 💡 **왜 `R`이 `T(-position)` 다음이어야 하는가:** 회전 행렬은 항상 **원점을 중심으로**
> 돈다. 카메라를 먼저 원점으로 끌어오지 않으면 월드 원점을 중심으로 돌아버려서,
> 카메라가 멀리 있을수록 화면이 크게 휩쓸린다. **"회전시키고 싶은 중심을 먼저 원점으로
> 옮긴다"** 는 것이 회전 변환의 기본 패턴이다. (B-10에서 우주선을 그릴 때 또 나온다)

### ⭐ 언제 순서를 바꿔도 되는가 — 교환법칙이 성립하는 예외

`AB ≠ BA`가 일반 원칙이지만, **균등 스케일과 회전은 교환된다.**

```
S(s) · R(θ) = R(θ) · S(s)      ← 균등 스케일이면 성립
```

직관: "2배 키우고 30도 돌리기"와 "30도 돌리고 2배 키우기"는 같은 결과다.
스케일이 모든 방향에 똑같이 걸리니까 회전과 간섭하지 않는다.

그런데 **비균등 스케일이면 깨진다.**
```
S(2, 1) · R(45°)  ≠  R(45°) · S(2, 1)
```
가로만 2배 늘린 다음 돌리는 것과, 돌린 다음 가로만 늘리는 것은 완전히 다르다
(전자는 기울어진 타원, 후자는 다른 방향의 기울어진 타원).

> 📚 **"교환법칙이 성립하지 않는다"를 외우는 것보다 "언제 성립하는가"를 아는 게 깊이다.**
> 우리는 균등 스케일만 쓰므로 `S·R` 순서를 바꿔도 결과가 같다.
> **B-2의 검증 항목에서 이걸 직접 확인해볼 것** — 다른 순서 조합은 다른데
> 이 조합만 같다는 걸 보면 이해가 굳는다.

### 순서를 바꾸면 무슨 일이 나는가 (⭐ 반드시 실험할 것)

`S(zoom)`을 맨 앞으로 옮겨보자. `S(zoom) * T(half) * T(-position)`

전개하면 `screen = zoom · (world - position + half)` 가 된다.
올바른 식 `zoom · (world - position) + half` 과 비교하면 **`half`까지 zoom이 곱해진다.**

- zoom = 1 일 때는 **똑같아 보인다** (그래서 초기에 못 잡는다)
- zoom = 0.01 로 줌아웃하면 화면 중앙 오프셋 `(240, 400)`이 `(2.4, 4)`로 줄어
  **모든 것이 화면 좌상단 구석으로 빨려 들어간다**

> 💡 **행렬 곱은 교환법칙이 성립하지 않는다(`AB ≠ BA`)** 를 글로 읽는 것과
> 이 버그를 직접 보는 것은 완전히 다르다. **일부러 순서를 바꿔서 화면이 깨지는 걸
> 눈으로 확인하고, 스크린샷을 남겨라.** 1주차 최고의 학습이자 회고 자료다.

### 검산식 (구현 후 반드시 확인)

**1단계 — 회전 없이 (`θ = 0`, `R = I`)**

`T(half) · S(s) · T(-c)` 를 손으로 전개하면:

```
      | s  0   -s·cx + hx |
  V = | 0  s   -s·cy + hy |
      | 0  0        1     |
```

`(x, y, 1)`을 곱하면:
```
x' = s·x - s·cx + hx = (x - cx)·s + hx
y' = s·y - s·cy + hy = (y - cy)·s + hy
```

> **`screen = (world - cameraPos) · zoom + half`**

**2단계 — 회전까지 (`θ ≠ 0`)**

`S(s)·R(θ)` 의 좌상단 2x2는 이렇게 된다:
```
  A = | s·cosθ  -s·sinθ |
      | s·sinθ   s·cosθ |
```
`T(-c)`가 붙으면 이동 항이 `A·(-c)`가 되고, 마지막 `T(half)`가 `+h`를 더한다:

> **`screen = zoom · Rotate(world - cameraPos, θ) + half`**

`θ = 0`을 넣으면 1단계 식으로 정확히 돌아온다. ✅

**검증 순서:** 먼저 `θ = 0`으로 1단계 식과 대조해 곱셈·조립을 확인하고,
그다음 `θ ≠ 0`으로 2단계 식과 대조한다. **한 번에 둘 다 틀리면 어디가 문제인지 못 찾는다.**
(Part C의 테스트도 이 순서로 되어 있다)

## A-4. 좌표 공간 3단

```
[ World 좌표 ]  게임 로직·물리가 사는 곳. 우주선이 (1200000, -30000)에 있다.
      │  × View 행렬
      ▼
[ Screen 좌표 ]  화면 픽셀. (240, 400)이 화면 중앙.  ← GDI가 그리는 곳
      │  × 레터박스 변환 (GameInstance가 처리)
      ▼
[ Window 좌표 ]  실제 창 픽셀. 창 크기에 따라 달라진다.  ← 마우스가 사는 곳
```

**중요한 원칙:** 물리·게임 로직은 **World 좌표만** 안다. 화면이 얼마나 확대됐는지,
창이 얼마나 커졌는지 전혀 신경 쓰지 않는다. 변환은 **렌더링 직전에 딱 한 번**만 일어난다.

이 분리가 깨지면 "줌아웃했더니 중력이 약해지는" 식의 버그가 난다.

> ⚠️ **마우스 입력은 거꾸로 두 번 변환해야 한다.**
> `Window 좌표 → (레터박스 역변환) → Screen 좌표 → (뷰 역행렬) → World 좌표`
> `GameInstance::GetGameViewportRect()`가 첫 단계에 필요한 사각형을 준다.
> 이 프로젝트는 창 크기가 변해도 게임 논리 해상도(480x800)가 고정이라
> **레터박스 변환을 빼먹으면 창을 키웠을 때만 클릭이 어긋난다** (창이 원래 크기면 정상).

## A-5. 역행렬 — 화면에서 월드로 되돌리기

### 무엇을 위한 것인가

기획서의 **"우주선을 클릭하면 카메라 모드가 바뀐다"** 를 구현하려면,
마우스가 찍은 **화면 좌표**를 **월드 좌표**로 되돌려서 "우주선 근처인가?"를 판정해야 한다.

`WorldToScreen`이 `V`라면, 되돌리는 건 `V⁻¹`. 그게 전부다.

### 일반 3x3 역행렬 (여인수 전개)

```
det = m00·(m11·m22 - m12·m21)
    - m01·(m10·m22 - m12·m20)
    + m02·(m10·m21 - m11·m20)

M⁻¹ = (1/det) · adj(M)
```

`adj(M)`(수반행렬)은 **여인수 행렬의 전치**다. ⚠️ **전치를 빼먹는 게 최고 빈출 실수.**

### 아핀 전용 역행렬 (실제로 쓸 것)

우리 행렬은 마지막 행이 **항상 `0 0 1`** 이다. 이 성질을 쓰면 훨씬 짧아진다.
행렬을 블록으로 쪼개면:

```
M = | A  t |          A = 좌상단 2x2 (스케일·회전)
    | 0  1 |          t = 이동 (3열의 위 두 개)
```

이때 역행렬은:

```
M⁻¹ = | A⁻¹   -A⁻¹t |
      |  0       1  |
```

2x2 역행렬은 공식이 간단하다:
```
A = | a  b |        A⁻¹ = (1/det) · |  d  -b |        det = a·d - b·c
    | c  d |                        | -c   a |
```

### 이 식이 말하는 것 (⭐ 여기가 학습 포인트)

이동 부분이 그냥 `-t`가 **아니라** `-A⁻¹t`인 게 핵심이다.

의미: **"먼저 스케일/회전을 되돌리고, 그 되돌린 좌표계에서 이동을 뺀다."**

왜 그런가 — 원래 변환이 `p' = A·p + t` 였으니, 거꾸로 풀면:
```
p' - t = A·p
A⁻¹(p' - t) = p
p = A⁻¹p' - A⁻¹t        ← 이동 항에도 A⁻¹가 곱해진다
```

순서를 반대로 (이동 먼저 빼고 스케일 되돌리기) 하면 **줌 배율만큼 어긋난다.**
zoom=1일 때는 또 멀쩡해 보이므로, 반드시 줌을 바꿔가며 테스트할 것.

### ⭐ 회전이 들어오면 이게 훨씬 중요해진다

회전이 없을 때 `A`는 **대각행렬**이었다:
```
A = | s  0 |     ← 대각선만 값이 있음
    | 0  s |
```
이런 행렬은 역행렬도 대각행렬(`1/s`)이라 **틀린 구현이 우연히 비슷한 답을 내기 쉽다.**

회전이 들어가면 `A`는 네 성분이 모두 살아있는 **진짜 2x2**가 된다:
```
A = | s·cosθ  -s·sinθ |
    | s·sinθ   s·cosθ |
```
이제 `-A⁻¹t`를 `-t`로 잘못 쓰면 **틀린 방향으로, 틀린 거리만큼** 어긋난다.
우연히 맞을 여지가 사라진다.

> 💡 **이건 나쁜 소식이 아니라 좋은 소식이다.** 조용히 틀린 코드보다 시끄럽게
> 틀린 코드가 훨씬 낫다. 회전을 넣기로 한 덕분에 **역행렬 구현의 검증력이 올라갔다.**
> `zoom ≠ 1` **그리고** `rotation ≠ 0` 인 상태에서 클릭 피킹이 정확하면,
> 역행렬이 진짜로 맞은 것이다.

### 예외 처리

`det`이 0에 가까우면 역행렬이 존재하지 않는다 (줌이 0이면 모든 점이 한 점으로 뭉개져
되돌릴 정보가 사라진다). 이때는 항등행렬을 반환하고 빠져나온다.
`SMALL_NUMBER`(`1.e-8f`)가 `pch.h`에 이미 정의되어 있으니 그걸 쓴다.

### 왜 두 개를 다 만드는가

실제로 쓰는 건 아핀 버전 하나다. 일반 버전은 **"내 지름길이 진짜 역행렬과 같은가"를
검증하는 참조 구현**이다. 게임 코드에서 최적화할 때 항상 필요한 습관 —
느리지만 확실한 버전을 옆에 두고 대조한다. 확인 후에도 지우지 말고 남겨서 회고 자료로 쓴다.

## A-6. 로그(지수) 줌 보간 — 왜 선형 lerp가 아닌가

### 문제

지표면 클로즈업(`zoom = 10`)에서 태양계 전경(`zoom = 0.001`)까지 가야 한다.
**1만 배 차이**다. 선형 보간으로 중간(t=0.5)을 잡으면:

```
zoom = 10 + (0.001 - 10) × 0.5 ≈ 5.0
```

`10 → 5`는 눈으로 보면 "거의 안 움직였다". 그런데 남은 절반 동안 `5 → 0.001`을
가야 하므로 **끝에서 갑자기 튄다.** 애니메이션이 앞은 굼뜨고 뒤는 폭발한다.

### 왜 그런가 — 줌은 곱셈적이다

사람이 느끼는 "확대량"은 **비율**이다.
`1배 → 2배`와 `100배 → 200배`는 **같은 정도의 변화로 느껴진다.** (둘 다 2배)
차이(`+1` vs `+100`)는 전혀 다른데도 그렇다.

즉 줌은 덧셈 공간이 아니라 **곱셈 공간**에 산다.
곱셈을 덧셈으로 바꾸는 도구가 바로 **로그**다.

### 해법

`zoom` 대신 `log(zoom)`을 선형 보간한다.

```
log(z) = (1-t)·log(z₀) + t·log(z₁)
   z   = z₀^(1-t) · z₁^t          ← 양변에 exp
```

t=0.5면 `z = √(z₀·z₁)` — **산술평균이 아니라 기하평균**이다.
`10`과 `0.001`의 기하평균은 `0.1`. 양쪽으로 100배씩 — 대칭이다. ✅

### 프레임 독립성까지 챙기기

매 프레임 `z += (target - z) * 0.1f` 같은 코드는 **프레임레이트에 따라 속도가 달라진다.**
(60fps와 30fps에서 다르게 움직임)

지수 감쇠로 쓰면 dt에 무관해진다. `k`는 속도 상수(클수록 빠름, 5~10 정도부터 시작):

```
a = exp(-k · dt)          ← 이번 프레임에 "남길 비율"
z = z₀^a · z₁^(1-a)       ← 로그 공간에서의 지수 감쇠
```

구현 시엔 `pow(target/current, 1 - a)`를 현재 값에 곱하는 형태가 편하다.
(두 식이 같음은 지수법칙으로 직접 확인해볼 것 — 좋은 연습이다)

> 💡 **같은 원리가 2주차에도 나온다.** 고도에 따른 하늘색 전환, 3주차 카메라 추적도
> 전부 "지수 감쇠로 목표를 따라가기"다. 여기서 한 번 제대로 만들어두면 계속 재사용된다.

## A-7. 이 프로젝트의 좌표계 함정

### y축이 아래로 증가한다 (GDI/WinAPI)

```
   (0,0) ────────► x
     │
     │      화면
     ▼ y
```

결과로 생기는 것들:
- **"위"는 `(0, -1)`이다.** 기존 코드가 이미 그렇게 짜여 있다
  (`AActor.cpp`의 `_forwardDir = Vector2(0,-1).Rotate(radian)`)
- 수학 관례의 **반시계 회전이 화면에서는 시계 방향으로 보인다**
- 각도 부호가 헷갈리면 **기존 `AActor::SetRotation`의 관례를 따라간다** (단일 소스)

### 화면 해상도는 480 x 800 (세로형)

`GWinSizeX = 480`, `GWinSizeY = 800` (`pch.h`). **화면 중앙은 `(240, 400)`.**
로켓 상승 게임이라 세로가 유리하다. 정사각형이 아니므로
`half`를 계산할 때 x/y를 각각 나눠야 한다 (한 값으로 퉁치지 말 것).

### 카메라의 `_width/_height`가 지금 안 쓰이고 있다

현재 `Camera::WorldToScreen`은 `Init`으로 받은 `_width/_height`를 저장해놓고
정작 전역 `GWinSizeX/Y`를 쓴다. **멤버 값을 쓰도록 통일**할 것.
그래야 `Init(width, height)`가 의미를 갖고, 나중에 미니맵처럼 다른 크기의
뷰포트를 만들 때 그대로 재사용된다.

## A-8. 표면 정렬 각도 구하기

**목표:** 행성 위 어떤 지점에 있든, 그 지점의 "로컬 위"가 **화면 위쪽**을 향하게 만든다.

### 1단계 — 로컬 "위" 방향

행성 표면에서 "위"는 **행성 중심에서 바깥으로** 나가는 방향이다.

```
u = (기준점 - 행성중심).Normalized()
```

(기준점 = 카메라가 보고 있는 지점, 보통 우주선 위치)

### 2단계 — 그 방향이 지금 몇 도인가

```
φ = atan2(u.y, u.x)
```

> 💡 **`atan2(y, x)`가 `atan(y/x)`보다 나은 이유:** `atan`은 나눗셈을 하는 순간
> 사분면 정보를 잃는다. `(1,1)`과 `(-1,-1)`은 `y/x`가 둘 다 `1`이라 구분이 안 된다.
> `atan2`는 y와 x의 **부호를 따로** 보므로 네 사분면을 모두 구분하고, `x=0`도 처리한다.
> **방향에서 각도를 뽑을 땐 항상 `atan2`.** 이건 게임 코드 전반의 습관이다.

### 3단계 — 얼마나 돌려야 하는가

우리가 원하는 목적지는 **화면 위쪽 `(0, -1)`** 이다. (A-7 — y축이 아래로 증가하므로)
이 방향의 각도는 `atan2(-1, 0) = -π/2`.

회전 행렬 `R(θ)`는 각도 `φ`인 벡터를 각도 `φ + θ`로 보낸다. 그러니:

```
φ + θ = -π/2
      ↓
θ = -π/2 - φ
```

이게 뷰 행렬에 넣을 회전각이다. **유도는 이게 전부다.**

### 4단계 — 고도에 따라 풀어주기

지표면에서만 정렬하고, 우주로 나가면 정렬을 푼다.

```
t = clamp(altitude / atmosphereHeight, 0, 1)     // 0=지표면, 1=대기권 밖

θ_target = LerpAngle(surfaceAngle, 0, ease(t))
```

**같은 `t`가 이미 줌·하늘색·별 밝기를 구동하고 있다.** 회전이 네 번째로 붙는 것뿐이다.

**판단할 것:** `ease()`를 어떤 곡선으로? 선형이면 정렬이 풀리는 게 밋밋하고,
smoothstep(`t*t*(3-2*t)`)이면 시작과 끝이 부드럽다. 직접 비교해볼 것.

> ⚠️ **검증 방법:** 발사대를 행성의 **여러 지점**(위, 아래, 옆구리)에 놓고
> 매번 지평선이 수평인지 확인한다. 한 지점만 테스트하면 부호 실수를 못 잡는다.
> 특히 `θ = -π/2 - φ` 의 부호를 `+π/2 - φ` 나 `φ - π/2` 로 잘못 써도
> **특정 위치에서는 우연히 맞아 보인다.**

## A-9. 각도 보간과 최단경로 — 이 코드베이스의 함정

### 문제

`350°`에서 `10°`로 회전한다고 하자. 사람은 당연히 **+20°** 로 갈 거라 기대한다.
그런데 순진하게 보간하면:

```
lerp(350, 10, t) = 350 + (10 - 350)·t = 350 - 340·t
```
**-340°**, 즉 한 바퀴를 거꾸로 되돌아 돈다. 카메라가 빙글 돌아버린다.

### 해법 — 차이를 ±180° 안으로 접는다

```
delta = target - current
while (delta >  π)  delta -= 2π
while (delta < -π)  delta += 2π

result = current + delta · t
```

또는 한 줄로: `delta = atan2(sin(d), cos(d))` (사인/코사인을 거치면 자동으로 접힌다)

`350 → 10`이면 `delta = -340` → `+20`으로 접힌다. ✅

### ⚠️ 이 프로젝트 고유의 함정

`Core/Util.cpp`의 두 함수를 보자.

```cpp
float RadianToDegree(float radian)   // Util.cpp:5
{
    degree = fmodf(degree, 360.0f);
    if (degree < 0.0f) degree += 360.0f;   // ← [0, 360)으로 정규화
    return degree;
}

float DegreeToRadian(float degree)   // Util.cpp:16
{
    radian = fmodf(radian, pi*2);
    if (radian < 0.0f) radian += pi*2;     // ← [0, 2π)로 정규화
    return radian;
}
```

**두 함수 모두 음수를 양수로 바꿔버린다.** 그래서:
- `-20°`를 넣으면 `340°`가 나온다
- **각도 "차이"를 이 함수에 통과시키면 최단경로 정보가 파괴된다**

> 📌 **`LerpAngle`을 만들 때 `DegreeToRadian`을 중간에 끼워넣지 말 것.**
> 이 함수들은 "각도 → 각도" 변환용이지 "차이 계산"용이 아니다.
> 기존 코드의 편의 함수를 재사용하는 건 좋은 습관이지만, **그 함수가 무슨 짓을
> 하는지 확인하고 쓰는 것**이 더 중요하다. 이게 남의 코드베이스에 들어갈 때
> 항상 필요한 태도다.

## A-10. 왜 행렬을 그냥 섞으면 안 되는가 (⭐ 회전이 들어온 대가)

카메라 모드 전환(고정 ↔ 우주선 중심)은 두 상태 사이를 부드럽게 이어야 한다.
가장 순진한 방법은 **두 뷰 행렬의 성분을 하나씩 선형 보간**하는 것이다.

```
result.m[i][j] = a.m[i][j]·(1-t) + b.m[i][j]·t
```

회전이 없을 땐 이게 잘 돌아간다. 그런데 회전이 들어오면 **깨진다.**

### 얼마나 깨지는가 — 직접 계산해보자

**예시 1: `R(0°)` → `R(180°)` 의 중간(t=0.5)**
```
R(0°) = | 1  0 |        R(180°) = | -1   0 |
        | 0  1 |                  |  0  -1 |

성분별 평균 = | 0  0 |     ← 영행렬!
              | 0  0 |
```
**모든 점이 한 점으로 뭉개진다. 화면이 사라진다.**

**예시 2: `R(0°)` → `R(90°)` 의 중간(t=0.5)**
```
R(0°) = | 1  0 |        R(90°) = | 0  -1 |
        | 0  1 |                 | 1   0 |

성분별 평균 = | 0.5  -0.5 |
              | 0.5   0.5 |
```
이 행렬의 각 열 길이는 `√(0.5² + 0.5²) ≈ 0.707`.
**회전 45°는 맞는데 스케일이 0.707배로 줄어들었다.**
전환 중에 화면이 30% 쪼그라들었다가 돌아온다.

### 왜 그런가

회전 성분은 `(cosθ, sinθ)` — **단위원 위의 점**이다.
단위원 위의 두 점을 **직선으로 이으면 원 안쪽을 지난다** (현이 호보다 짧으니까).
원 안쪽 = 길이가 1보다 작음 = **스케일 축소**.

```
      단위원
       ___
     ／     ＼
    |    ·    |     · = 두 점을 직선으로 이은 중간 지점
     ＼ _ _ ／        (원 위가 아니라 안쪽에 있다)
```

180° 차이일 땐 두 점이 정반대라 직선의 중간이 **정확히 원의 중심(=0)** 이 된다.
그래서 영행렬이 나오는 것이다.

### 올바른 방법 — 파라미터를 보간한다

행렬을 섞지 말고, **행렬을 만드는 재료를 각각 보간한 뒤 매 프레임 다시 조립**한다.

| 파라미터 | 보간 방식 | 근거 |
|---|---|---|
| 위치 | 선형 보간 | 위치는 덧셈 공간 |
| **각도** | **최단경로 보간** | A-9 |
| 줌 | **로그 보간** | A-6 (곱셈 공간) |

그리고 `T(half)·S(zoom)·R(θ)·T(-pos)` 로 매 프레임 재조립한다.

> 📚 **각 파라미터가 사는 공간이 다르다는 게 핵심이다.**
> 위치는 덧셈, 줌은 곱셈, 각도는 원 위. **셋을 뭉뚱그려 행렬 성분으로 섞으면
> 세 공간의 구조가 전부 무시된다.** 이게 A-6(로그 줌)과 A-9(각도 최단경로)에서
> 각각 배운 것이 하나로 합쳐지는 지점이다.

> 💡 **B-8에서 두 방식을 다 만들어본다.** 깨지는 걸 눈으로 본 다음 고치는 게
> 설명만 읽는 것보다 훨씬 오래 남는다. 그리고 그 실패 화면이 회고 자료가 된다.

## B-1. `Vector2::Normalized()` + const화 — `0-A`

**학습 근거:** A-1 (점/방향 구분)은 아니고, 순수 C++ 설계 문제다.

기존 `Normalize()`는 **자기 자신을 바꾼다(in-place)**. 물리 계산에서는
"원본은 두고 방향만 필요한" 경우가 훨씬 많으므로 **사본을 반환하는 버전**이 따로 필요하다.

**판단할 것:** 길이가 0에 가까울 때 무엇을 반환할 것인가?
`(0,0)`을 반환할지, `(1,0)` 같은 임의 방향을 줄지, assert로 잡을지.
→ 2주차에 우주선이 행성 중심에 정확히 겹치면 이 경우가 실제로 발생한다.
지금 정한 규칙을 주석으로 남겨둘 것.

**같이 할 것:** `Length`, `LengthSquared`, `Dot`, `Cross`, `Rotate`,
`operator+ - * /` 를 전부 `const`로. 안 그러면 `const Vector2&`를 받는 함수를 못 만든다.

**✅ 검증:** `(3,4)`의 `Length()`가 `5`. `Normalized()`의 `Length()`가 `1`.
`Normalized()` 호출 후에도 **원본이 `(3,4)` 그대로**인지 확인 (이게 핵심).

## B-2. `Matrix3x3` 기본 — `0-B`, `0-C`

**학습 근거:** A-1, A-2, A-3

`Identity` / `Translate` / `Scale` / `Rotate` 정적 생성자 + `operator*` + `TransformPoint` + `TransformVector`.

**함정 ①** — `operator*`에서 **결과를 자기 자신에 누적하지 말 것.**
읽는 중인 값을 덮어쓰면 뒤쪽 계산이 오염된다. 별도 결과 객체에 쓰고 반환한다.

**함정 ②** — `m[i][j]`가 i행 j열인지 i열 j행인지 **주석으로 못 박아라.**
이 규약이 흔들리면 전체가 조용히 전치(transpose)된 채로 돌아간다.
설계는 **행 우선(`m[행][열]`) + 열벡터(`p' = M·p`)** 로 정했다.

**✅ 검증 (순서대로):**
1. `Identity().TransformPoint((3,4))` → `(3,4)`
2. `Translate((10,20)).TransformPoint((3,4))` → `(13,24)`
3. `Translate((10,20)).TransformVector((3,4))` → `(3,4)` ← **이동 무시 확인**
4. `Scale(2).TransformPoint((3,4))` → `(6,8)`
5. `Rotate(90°).TransformPoint((1,0))` → `(0,1)` ← y-down 관례 확인 (A-7)
6. `Rotate(θ) * Rotate(-θ)` → 항등행렬
7. `(A * Identity())` 의 모든 성분이 `A`와 같은지
8. **`Translate(t) * Scale(s)` 와 `Scale(s) * Translate(t)` 의 결과가 다른지**
   ← 이게 다르지 않으면 곱셈 구현이 틀렸다
9. **`Scale(s) * Rotate(θ)` 와 `Rotate(θ) * Scale(s)` 의 결과가 같은지**
   ← A-3의 교환법칙 예외. **8번은 다르고 9번은 같아야 한다.**
   둘 다 같으면 곱셈이 틀린 것이고, 둘 다 다르면 회전/스케일 구현을 확인할 것

## B-3. 역행렬 2종 — `0-D`, `0-D'`

**학습 근거:** A-5

아핀 전용(`Inverse`)과 일반(`InverseGeneral`) 둘 다 만든다.

**함정 ①** — 일반 버전에서 **수반행렬의 전치**를 빼먹기 (최고 빈출)
**함정 ②** — 아핀 버전에서 이동 항을 `-t`로 두기 (`-A⁻¹t`가 맞다). **zoom=1에서는 안 보인다.**
**함정 ③** — `det ≈ 0` 처리 누락

**✅ 검증:**
1. 아무 뷰 행렬 `V`에 대해 `V * V.Inverse()` 가 **항등행렬**인지 (부동소수점 오차 감안)
2. `V.Inverse()` 와 `V.InverseGeneral()` 의 모든 성분이 일치하는지
3. **⚠️ 반드시 `zoom ≠ 1`로 테스트할 것.** `zoom = 0.01`, `zoom = 50` 두 경우 모두.
   zoom=1에서는 틀린 구현도 통과한다.

## B-4. 뷰 행렬 조합 — `1-A`, `1-A'`

**학습 근거:** A-3 (⭐ 1주차 핵심), A-4

`Camera::UpdateViewMatrix()`에서 `_view`와 `_invView`를 만든다.

**판단할 것:** `_invView`를 매 프레임 계산할까, 요청할 때 계산할까?
→ 뷰 행렬은 **프레임당 한 번만** 바뀌므로 미리 만들어두는 게 맞다.
   액터마다 역행렬을 다시 구하면 행렬을 쓰는 이득(합성 결과 재사용)이 사라진다.

**✅ 검증 (⭐ 가장 중요) — 회전을 0으로 두고 먼저, 그다음 회전을 켠다:**

*1단계 (`rotation = 0`)*
1. `zoom=1`, `position=(0,0)` 일 때 `WorldToScreen((0,0))` → `(240, 400)`
2. **A-3의 1단계 검산식과 대조:** `WorldToScreen(p)` 가
   `(p - position) * zoom + (240,400)` 과 일치하는가 (여러 zoom·position으로)
3. `ScreenToWorld(WorldToScreen(p)) == p` — 왕복이 제자리로 오는가 (**zoom≠1로!**)

*2단계 (`rotation ≠ 0`)*
4. **A-3의 2단계 검산식과 대조:** `WorldToScreen(p)` 가
   `zoom * Rotate(p - position, θ) + half` 와 일치하는가
5. `V * V.Inverse()` = 항등행렬 — **`zoom≠1` 그리고 `rotation≠0` 동시에**
6. `ScreenToWorld(WorldToScreen(p)) == p` — 역시 둘 다 켠 상태로
   ← A-5에서 말한 `-A⁻¹t` 검증의 핵심. 여기 통과하면 역행렬이 진짜 맞은 것

*실험*
7. **일부러 곱셈 순서를 바꿔보고** 화면이 어떻게 깨지는지 확인 → **스크린샷 남길 것**
   - `S`를 맨 앞으로 → 화면이 좌상단으로 빨려든다
   - `R`을 `T(-position)` **앞으로** → 카메라가 멀수록 화면이 크게 휩쓸린다

> ⚠️ **1단계를 통과하기 전에 회전을 켜지 말 것.** 둘 다 틀린 상태에서는
> 어느 쪽이 원인인지 구분할 수 없다.

## B-9. 카메라 모드 2종 + 보간 — `0-E'`, `0-E`, `1-D` (⭐ 2단계로 진행)

**학습 근거:** A-6 (로그 보간), A-9 (각도 최단경로), A-10 (성분 보간이 깨지는 이유)

`Fixed`(행성 기준 고정) ↔ `Follow`(우주선 중심). `Tab` 또는 우주선 클릭으로 토글.

> 📌 **B-8을 먼저 끝내야 이 단계가 성립한다.** 두 모드의 회전각이 실제로 달라야
> 성분 보간이 깨지는 걸 관찰할 수 있다. (`Fixed`는 정렬 0, `Follow`는 표면 정렬)

이 단계는 **일부러 틀린 방법을 먼저 만들어보고, 고친다.**

### 1단계 — 성분별 행렬 보간 (깨지는 걸 관찰용) `0-E'`

두 모드의 뷰 행렬을 각각 만들고 `Matrix3x3::Lerp`로 성분을 하나씩 섞는다.

**관찰할 것:**
- 두 모드의 **회전각 차이를 크게** 만들어두고 전환시킨다 (90° 이상, 가능하면 180°)
- 전환 **중간 프레임**에서 화면이 어떻게 되는가?
  - 90° 차이 → 화면이 약 30% 쪼그라들었다가 돌아온다
  - 180° 차이 → **화면이 한 점으로 사라진다** (A-10의 영행렬)
- 회전각 차이를 0으로 두면 멀쩡하다 ← 원인이 회전이라는 증거

> 📸 **여기서 반드시 스크린샷 또는 GIF를 남길 것.** 이게 회고 문서 자료다.
> "행렬을 그냥 섞으면 안 되는 이유"를 말이 아니라 그림으로 보여줄 수 있다.
> 지금 안 찍으면 3주차에 코드를 되돌려서 재현해야 한다.

### 2단계 — 파라미터 보간 (실제로 쓸 것) `0-E`

행렬을 섞지 말고 **재료를 각각 보간한 뒤 매 프레임 재조립**한다.

| 파라미터 | 보간 방식 | 참고 |
|---|---|---|
| 위치 | 선형 보간 | — |
| 각도 | **최단경로 보간** (±180° 접기) | A-9 |
| 줌 | **로그 보간** | A-6 (B-5에서 만든 것 재사용) |

전환 시작 시점에 현재 파라미터 3개를 스냅샷하고, `blend`를 0→1로 올리며 보간한다.

**판단할 것 ①** — 보간 곡선을 선형으로? ease-in-out으로?
→ 카메라 전환은 시작·끝이 부드러워야 멀미가 없다. smoothstep(`t*t*(3-2*t)`)이면 충분.

**판단할 것 ②** — 전환 **도중에** 다시 토글하면?
→ 현재 보간된 값을 새 스냅샷으로 삼으면 자연스럽게 이어진다.
   목표 값에서 시작하면 화면이 튄다. **직접 토글을 연타해보고 확인할 것.**

**⚠️ 함정** — `LerpAngle`을 만들 때 `Util.cpp`의 `DegreeToRadian`을 중간에 끼우지 말 것
(A-9 참고 — 각도를 [0,2π)로 정규화해서 최단경로 정보를 파괴한다).

**✅ 검증:**
1. 전환 중에 화면이 튀거나 쪼그라들지 않는가 (1단계와 비교!)
2. `350° → 10°` 상황을 만들어서 **짧은 쪽(+20°)으로 도는가**
3. **전환 도중에 클릭 피킹이 정확한가** ← `_invView`를 재조립 후에 다시 만들었는지
4. 전환 중 모드를 연타로 토글해도 자연스럽게 이어지는가

## B-10. 변환 합성 — 우주선 도형과 별 배경 — `1-G`

**학습 근거:** A-1 (점/방향), A-3 (합성)

카메라가 회전하면 **화면에 그리는 모든 것이 같이 돌아야 한다.**
여기서 처음으로 변환을 **2단으로 합성**한다.

### 우주선 도형

우주선을 로컬 좌표의 점 몇 개(예: 삼각형)로 정의하고, 두 단계를 거쳐 화면에 찍는다.

```
M = View · T(shipCenter) · R(shipAngle)

로컬 점들 → M.TransformPoint() → 화면 좌표 → Polygon()
```

오른쪽부터: 기체를 자기 각도로 돌리고 → 월드 위치로 옮기고 → 뷰 변환.

> 💡 **여기서 카메라 회전이 공짜로 따라온다.** 우주선의 화면상 각도를
> "기체 각도 + 카메라 각도"로 직접 계산할 필요가 없다.
> 행렬 합성이 알아서 처리한다 — **이게 행렬을 쓰는 두 번째 이득**이다.
> (첫 번째는 뷰 행렬을 프레임당 한 번만 만들어 재사용하는 것)

**판단할 것** — `M`을 매 프레임 만들 것인가? 우주선은 하나뿐이라 부담이 없지만,
"액터마다 행렬을 만든다"는 습관이 액터가 많아지면 비용이 된다.
언제 캐시하고 언제 즉석에서 만들지 기준을 세워둘 것.

### 별 배경

별을 **화면 좌표에 고정으로 찍으면 안 된다.** 월드만 돌고 별은 가만히 있어서
"내가 도는 게 아니라 세상이 도는" 이상한 느낌이 된다.

→ 별을 **월드 좌표의 점**으로 생성해두고, 렌더할 때 `View.TransformPoint()`를 통과시킨다.

**판단할 것** — 별을 얼마나 넓은 범위에 뿌릴 것인가?
카메라가 움직이면 별밭 밖으로 나갈 수 있다. 화면 밖 별을 컬링할지,
카메라 기준으로 재배치(무한 스크롤)할지 정할 것.

**✅ 검증:**
1. 카메라를 `Q`/`E`로 돌렸을 때 **우주선과 별이 화면과 함께** 도는가
2. 우주선을 `A`/`D`로 돌렸을 때 **우주선만** 도는가 (별은 가만히)
3. 줌아웃했을 때 우주선 도형이 같이 작아지는가

## 참고 — 막혔을 때 확인 순서

**변수를 하나씩 꺼서 범위를 좁힌다.**

1. **`rotation=0`으로 바꾸면 되는가?** → 되면 회전 관련
   (표면 정렬 부호, `R`의 곱셈 위치, 각도 보간)
2. **`zoom=1`로 바꾸면 되는가?** → 되면 줌 관련
   (역행렬 `-A⁻¹t`, 곱셈 순서)
3. **`position=(0,0)`으로 바꾸면 되는가?** → 되면 이동 관련
4. **창 크기를 원래대로 하면 되는가?** → 되면 레터박스 변환 누락
5. **행렬 성분을 직접 찍어서** A-3의 검산식과 대조
   (먼저 `rotation=0`인 1단계 식, 통과하면 2단계 식)
6. 그래도 모르겠으면 `Identity()`부터 한 단계씩 되짚기

> 💡 1~3번을 순서대로 하는 게 핵심이다. **회전 → 줌 → 이동** 순으로 끄면
> 가장 최근에 추가한 것부터 의심하게 되어 원인에 빨리 닿는다.
