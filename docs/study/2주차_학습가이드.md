## 2주차가 1주차와 다른 점

1주차는 **정적인 변환**이었다. 같은 입력을 넣으면 항상 같은 결과가 나오고,
틀리면 즉시 화면이 깨져서 알 수 있었다.

2주차는 **시간에 따라 누적되는 시스템**이다. 성격이 완전히 다르다.

| | 1주차 (변환) | 2주차 (물리) |
|---|---|---|
| 오류의 발현 | 즉시, 눈에 보임 | **수십 초 뒤에 서서히** |
| 검증 방법 | 한 프레임 값 대조 | **장시간 누적 관찰** |
| "조금 틀림" | 대개 크게 틀림 | **몇 분간 멀쩡하다 발산** |
| 디버깅 난이도 | 값을 찍으면 보임 | 값은 다 정상인데 결과가 틀림 |

> ⚠️ **그래서 2주차는 "해석해(정답을 아는 문제)"로 검증하는 게 필수다.**
> 자유낙하와 원궤도는 손으로 답을 낼 수 있다. 이 둘을 먼저 통과시키고
> 발사 시퀀스로 넘어가야 한다. Part C의 순서가 그렇게 짜여 있다.

# Part A. 공부 내용

## A-1. 물리 바디 — 무엇이 "상태"인가

### 상태(state)와 파생값(derived)

```
상태:   위치 x,  속도 v        ← 이것만 저장한다
파생:   가속도 a               ← 매 프레임 힘에서 다시 계산한다
```

**가속도를 멤버로 들고 다니면 안 된다.** 가속도는 "지금 이 위치에서 받는 힘"의
결과이고, 위치가 바뀌면 즉시 무효가 된다. 저장해두면 **한 프레임 전 위치 기준의
가속도**를 쓰게 되어 조용히 틀린다.

> 📌 **판단 기준: "이 값 없이 다음 프레임을 계산할 수 있는가?"**
> 위치·속도가 없으면 계산이 불가능하다 → 상태.
> 가속도는 위치에서 다시 만들 수 있다 → 파생.

### 힘 누적 패턴

한 프레임에 여러 힘이 작용한다 (중력, 추력, 나중엔 항력). 이걸 각각 즉시
속도에 반영하면 **적용 순서에 따라 결과가 달라진다.**

```
① 중력을 v에 반영 → ② 추력을 v에 반영     (순서 의존)
① 중력과 추력을 F에 더함 → ② F/m 을 한 번에 적분   ✅
```

물리적으로 힘은 **동시에** 작용하므로, 벡터로 먼저 합치고 마지막에 한 번만
적분해야 한다.

```
프레임 시작 → _force = (0,0)
            → AddForce(중력)
            → AddForce(추력)
            → Integrate(dt)   ← 여기서 a = F/m 계산 후 적분
            → _force = (0,0)  ← 반드시 리셋 (1주차 휠 델타와 같은 함정)
```

> ⚠️ **힘 리셋을 빼먹으면 매 프레임 힘이 누적되어 로켓이 지수적으로 가속한다.**
> 1주차 Day 1의 `_wheelDelta` 리셋 버그와 정확히 같은 구조다.
> 트러블슈팅 문서 **P2(프레임 내 실행 순서)** 의 재발이니 주의할 것.

## A-2. 뉴턴 제2법칙 — 그리고 질량이 사라지는 순간

### F = ma

```
a = F / m
```

여기까진 단순하다. 그런데 **중력에서는 이상한 일이 일어난다.**

### 중력에서 우주선 질량이 상쇄된다 ⭐

만유인력은 이렇게 생겼다:

```
F = G · m · M / r²        m = 우주선 질량, M = 행성 질량
```

이걸 `a = F/m`에 넣으면:

```
a = (G · m · M / r²) / m = G · M / r²
        ↑ 상쇄된다
```

**우주선의 질량이 사라진다.** 즉 **중력 가속도는 물체의 질량과 무관하다.**
깃털과 볼링공이 진공에서 같이 떨어지는 그 이야기가 코드에서 이렇게 나타난다.

### 그래서 μ 하나로 묶는다

`G`와 `M`이 항상 붙어 다니므로, 둘을 따로 들 이유가 없다.

```
μ (mu) = G · M          ← 중력 파라미터(gravitational parameter)
a_gravity = μ / r²
```

실제 천문학에서도 `G`와 `M`을 따로 재는 것보다 **`μ`를 직접 측정하는 게 훨씬
정확해서** 이 형태를 표준으로 쓴다 (지구 `μ = 3.986 × 10¹⁴ m³/s²`).

> 📌 **로드맵이 행성의 `mass`를 0으로 두고 시작한 것**과 이게 연결된다.
> 행성마다 필요한 건 질량이 아니라 `μ` 하나다. `APlanet`에 `_mu`를 두는 게
> `_mass`를 두고 매번 `G`를 곱하는 것보다 낫다.

### 그럼 우주선 질량은 어디에 쓰이는가

**추력에만 쓰인다.** 추력은 로켓이 스스로 내는 힘이라 상쇄되지 않는다.

```
a_thrust = F_thrust / m         ← 질량이 남아있다
a_gravity = μ / r²              ← 질량이 사라졌다
```

연료를 태우면 질량이 줄어 같은 추력으로 더 큰 가속을 얻는다 — 이게 로켓
방정식의 출발점이다. **이번 주차에서 연료 소모까지 넣을지는 선택이다**
(로드맵 필수 항목은 아니다).

> 💡 **간단히 가려면 우주선 질량을 `1`로 두면 된다.** 그러면 `F = a`가 되어
> 추력을 "가속도"로 직접 다룰 수 있다. 물리적 정확성을 잃지는 않는다
> (단위계를 그렇게 정한 것뿐). 나중에 연료를 넣을 때 질량을 살리면 된다.

## A-3. 만유인력의 벡터 형태

### 크기만으로는 부족하다

`F = μ/r²`는 **크기**다. 방향을 붙여야 벡터가 된다.

```
d = P_planet - P_ship          ← 우주선에서 행성을 향하는 벡터
r = |d|                        ← 거리
d̂ = d / r                      ← 단위 방향벡터

a = (μ / r²) · d̂
```

### 계산을 한 번에 — r³ 형태 ⭐

위 식을 풀어 쓰면:

```
a = (μ / r²) · (d / r) = μ · d / r³
```

**`d`를 정규화하지 않고 `r³`으로 한 번에 나눈다.** 이렇게 하면:
- `sqrt`를 한 번만 호출 (`Normalized()` 안에서 또 부르지 않음)
- 나눗셈이 세 번(정규화 2 + 크기 1)에서 한 번으로

```cpp
float r2 = d.LengthSquared();       // sqrt 없음
float r  = std::sqrt(r2);
float r3 = r2 * r;
Vector2 a = d * (mu / r3);
```

> 💡 **이건 "미세 최적화"가 아니라 관용구다.** 중력 계산은 n-body에서 매 프레임
> 수천 번 돌기 때문에, 물리 엔진 코드에서 `r³` 형태를 보게 되면
> "아 정규화를 합친 거구나"로 바로 읽혀야 한다.

### r → 0 특이점 ⚠️

우주선이 행성 중심에 정확히 겹치면 `r³ = 0` → **0으로 나눔 → NaN 또는 무한대.**
한 번 `NaN`이 되면 이후 모든 연산이 `NaN`으로 전염되어 우주선이 화면에서 사라진다.

두 가지 대응이 있다:

**① 소프트닝 (softening)** — 분모에 작은 값을 더해 특이점을 없앤다
```
r_soft² = r² + ε²
a = μ · d / (r_soft²)^1.5
```
n-body 시뮬레이션의 표준 기법. 물리적으로는 "점질량이 아니라 퍼진 질량"으로
근사하는 것에 해당한다.

**② 표면 반지름으로 클램프** — 이 게임에 더 맞다
```
r = max(r, bodyRadius)
```
어차피 `r < bodyRadius`면 지표면에 충돌한 것이라 게임이 끝난다(A-8).
행성 내부의 중력을 정확히 다룰 이유가 없다.

> 📌 **이 프로젝트는 ②를 권한다.** 다만 **왜 ①이 있는지 알아두면**
> "n-body를 왜 뺐는가"(로드맵)를 설명할 때 근거가 된다.

### ⚠️ 방향 부호는 반드시 눈으로 확인할 것

`d = P_planet - P_ship`인지 `P_ship - P_planet`인지 한 글자 차이로 **중력이
척력이 된다.** 우주선이 행성에서 날아가버리면 부호를 뒤집은 것이다.

이건 **테스트 없이는 못 잡는다.** 부호가 반대여도 코드는 멀쩡히 돌아가고
숫자도 정상으로 보인다. Part C-1의 자유낙하 테스트가 이걸 잡는다.

### ⚠️ 균일 중력을 상수로 쓸 때의 부호 (LaunchWorld)

행성이 없는 평면 월드에서는 중력을 상수로 쓴다. 이때 **"아래"가 `+y`다.**

```
아래(중력 방향) = (0, +20)      ✅
위              = (0, -20)      ← 이걸 쓰면 우주선이 날아오른다
```

GDI는 y축이 **아래로** 증가하기 때문이다 (1주차 학습가이드 A-7).
`AActor::_forwardDir = Vector2(0,-1)`이 "정면 = 화면 위"인 것과 같은 관례다.

> 💡 같은 이유로 **평면 월드의 고도는 `-y`** 다. 지면이 `y = 0`이고 위로 갈수록
> `y`가 음수가 되므로, 화면에 표시할 때 부호를 뒤집어야 자연스럽게 읽힌다.

## A-4. 게임 단위계 설계 — G를 실제값으로 쓰면 안 되는 이유

### 실제 값을 넣으면 어떻게 되는가

```
G = 6.674 × 10⁻¹¹
지구 M = 5.972 × 10²⁴ kg
지구 반지름 = 6.371 × 10⁶ m
```

`float`의 유효숫자는 약 7자리다. `10⁻¹¹`과 `10²⁴`를 곱하는 순간 정밀도가
녹아내리고, 좌표를 미터로 쓰면 **지구 반지름만 637만**이라 화면 좌표로 옮길 때
또 문제가 생긴다.

**게임은 자기만의 단위계를 정의한다.** 물리 법칙의 *형태*만 지키면 되지
SI 단위를 쓸 이유가 전혀 없다.

### 역산으로 정하는 게 편하다 ⭐

"μ를 얼마로 할까"는 감이 안 온다. 대신 **체감할 수 있는 값에서 거꾸로 구한다.**

```
표면 중력 g = μ / R²          (R = 행성 반지름)
        ↓ 뒤집으면
μ = g · R²
```

`g`는 "지표면에서 초당 속도가 얼마나 붙는가"라 감이 온다.
1주차에서 행성 반지름을 `R = 1000`으로 정했으니:

```
g = 20 units/s²  로 정하면
μ = 20 × 1000² = 2.0 × 10⁷
```

**왜 20인가:** 우주선 크기가 8이니 1초 자유낙하하면 10 units 떨어진다
(≈ 우주선 크기). 눈으로 "떨어지는구나"가 바로 보이면서 너무 빠르지도 않다.

### 이 단위계에서 파생되는 값들

정한 `μ`에서 나머지가 전부 따라 나온다. **이 숫자들을 미리 계산해두면
디버깅할 때 "지금 값이 말이 되는가"를 즉시 판단할 수 있다.**

| 양 | 공식 | 이 프로젝트 값 |
|---|---|---|
| 표면 중력 | `μ / R²` | `20 units/s²` |
| 원궤도 속도 (고도 300) | `√(μ/r)`, r=1300 | **`≈ 124 units/s`** |
| 탈출 속도 (지표면) | `√(2μ/R)` | **`200 units/s`** |
| 궤도 주기 (r=1300) | `2πr / v` | `≈ 66초` |

> 📌 **원궤도 속도 `√(μ/r)`는 이번 주차에서 가장 많이 쓸 식이다.**
> Part C의 핵심 테스트가 "이 속도를 정확히 주면 완전한 원이 나오는가"이고,
> 3주차 궤도 판정의 기준선이기도 하다. 유도는 A-6에서 한다.

## A-5. 수치적분 ⭐⭐ — 2주차의 심장

> 이 절이 2주차 전체에서 가장 중요하다. **면접에서 가장 자주 물어볼 주제이기도 하다.**
> 천천히 읽고, 반드시 세 개를 다 구현해서 직접 비교할 것.

### A-5-1. 왜 "적분"인가

우리가 아는 건 **가속도**뿐이다. 그런데 그리고 싶은 건 **위치**다.

```
a = μ/r² 로 주어짐
        ↓ 적분
v(t) = ∫ a dt
        ↓ 적분
x(t) = ∫ v dt
```

문제는 `a`가 `r`에, 즉 **위치에 의존한다**는 것이다. 위치를 알아야 가속도를
알고, 가속도를 알아야 위치를 안다. **서로 물고 있는 미분방정식**이라 일반적으로
손으로 풀 수 없다.

> 💡 2체 문제(우주선 + 행성 하나)는 예외적으로 해석해가 존재한다(케플러).
> 하지만 **추력이 붙는 순간 해석해는 사라진다.** 그래서 수치적분이 필요하다.

### A-5-2. 수치적분의 기본 아이디어

"아주 짧은 시간 `dt` 동안은 가속도가 일정하다고 치자."

```
v_new = v + a·dt
x_new = x + v·dt
```

`dt`가 작을수록 정확하다. 그런데 **작을수록 계산 횟수가 늘어난다.**
이 트레이드오프를 얼마나 잘 다루느냐가 적분기의 품질이다.

### A-5-3. ① 명시적 오일러 (Explicit / Forward Euler)

```
x_{n+1} = x_n + v_n · dt          ← 위치를 먼저, 옛 속도로
v_{n+1} = v_n + a(x_n) · dt
```

**두 갱신 모두 "이전 상태"만 사용한다.** 가장 직관적이고 가장 먼저 떠오르는 형태다.

**결과: 궤도가 바깥으로 나선을 그리며 발산한다.**

왜 그런가 — 원궤도를 생각해보자. 진짜 궤도는 원이므로 속도 방향이 계속 휘어야
하는데, 오일러는 **한 스텝 동안 직선으로 간다.** 원의 접선은 항상 원 바깥에
있으므로, 매 스텝마다 조금씩 바깥으로 밀린다.

```
      진짜 궤도(원)          오일러의 한 스텝
         ___                    ___
       ／    ＼               ／    ＼
      |   ●   |              |   ●   |──→ 접선을 따라 직선
       ＼ _ ／                ＼ _ ／     (원 바깥으로 벗어남)
```

**에너지 관점**: 이 "바깥으로 밀림"은 매 스텝 역학적 에너지를 조금씩 **더한다.**
에너지는 단조 증가하고, 결국 탈출 속도를 넘어 우주선이 날아가버린다.

> ⚠️ **`dt`를 줄여도 발산 자체는 막지 못한다.** 발산이 느려질 뿐이다.
> 이게 "정확도"와 "안정성"이 다른 문제라는 첫 번째 증거다.

### A-5-4. ② 반암시적 오일러 (Semi-implicit / Symplectic Euler) ⭐

```
v_{n+1} = v_n + a(x_n) · dt       ← 속도를 먼저
x_{n+1} = x_n + v_{n+1} · dt      ← 새 속도를 사용
```

**바뀐 건 두 줄의 순서와 `v_n → v_{n+1}` 하나뿐이다.**
그런데 **결과가 질적으로 완전히 다르다.**

**결과: 에너지가 유계 안에서 진동한다. 발산하지 않는다.**

```
  명시적 오일러                반암시적 오일러
  E │      ╱                  E │  ∿∿∿∿∿∿∿∿∿∿
    │    ╱                      │  (일정 폭으로 진동)
    │  ╱                        │
    └──────── t                 └──────── t
    단조 증가 → 발산             유계 진동 → 안정
```

### A-5-5. 왜 한 줄 순서가 그렇게 큰 차이를 만드는가 ⭐⭐

이게 이번 주차 최고의 학습 포인트다.

반암시적 오일러는 **심플렉틱(symplectic) 적분기**다. 심플렉틱 적분기는
**위상공간(phase space)의 부피를 정확히 보존한다.**

위상공간이란 `(위치, 속도)`를 축으로 하는 공간이다. 물리계가 시간에 따라
변하면 이 공간의 점이 움직이는데, **해밀턴 역학은 "부피가 보존된다"**
(리우빌 정리)고 말한다.

- **명시적 오일러**: 부피가 매 스텝 팽창한다 → 에너지가 새어 들어온다
- **반암시적 오일러**: 부피가 정확히 보존된다 → 에너지가 갇힌다

더 정확히 말하면, 심플렉틱 적분기는 **원래 에너지 `H`를 보존하지는 않지만,
그것과 아주 가까운 다른 에너지 `H̃ = H + O(dt)`를 정확히 보존한다.**
그래서 에너지 오차가 **누적되지 않고 진동**한다.

> 📚 **이 문장 하나를 이해하고 설명할 수 있으면 면접에서 강하다.**
> "왜 게임 물리 엔진이 대부분 반암시적 오일러를 쓰는가"에 대한 답이 이것이다.
> Box2D, Bullet, Unity의 기본 적분기가 전부 이 계열이다.

### A-5-6. ③ RK4 (4차 룽게-쿠타)

한 스텝 안에서 기울기를 **네 번** 재서 가중평균한다.

상태를 `y = (x, v)`로 묶고, 변화율을 `f(y) = (v, a(x))`라 하면:

```
k1 = f(y)
k2 = f(y + (dt/2)·k1)
k3 = f(y + (dt/2)·k2)
k4 = f(y + dt·k3)

y_{n+1} = y_n + (dt/6)·(k1 + 2·k2 + 2·k3 + k4)
```

**가중치 `1:2:2:1`의 의미**: 중간 지점(k2, k3)에서 잰 기울기를 두 배로
신뢰한다. 심프슨 공식과 같은 구조로, 이 조합이 4차 정확도를 만든다.

**정확도**: 전역 오차가 `O(dt⁴)`다. `dt`를 절반으로 줄이면 오차가 **1/16**이
된다 (오일러는 1/2). 압도적이다.

### A-5-7. ⭐ 반전 — RK4는 심플렉틱이 아니다

정확도만 보면 RK4가 완승이다. 그런데 **장시간 궤도 시뮬레이션에서는
반암시적 오일러가 더 나을 수 있다.**

RK4는 심플렉틱이 아니라서 **에너지가 서서히 감소(소산)한다.** 짧은 시간엔
오차가 워낙 작아 티가 안 나지만, 수천 궤도를 돌리면 궤도가 조금씩 안쪽으로
말려든다.

| | 정확도 | 에너지 보존 | 비용 (힘 계산) |
|---|---|---|---|
| 명시적 오일러 | `O(dt)` | ❌ 증가 → 발산 | 1회 |
| **반암시적 오일러** | `O(dt)` | ✅ **유계 진동** | 1회 |
| RK4 | `O(dt⁴)` | ⚠️ 서서히 감소 | **4회** |

> 📚 **"정확도 ≠ 보존성"** — 이 대비가 2주차 회고의 하이라이트다.
> 목적에 따라 좋은 적분기가 달라진다는 것, 그리고 **"더 정확한 게 항상 답은
> 아니다"** 는 것. 이걸 직접 측정한 그래프로 보여줄 수 있으면 아주 강하다.

### A-5-8. RK4가 강제하는 설계 제약 ⭐

RK4 구현에서 반드시 막히는 지점이 있다.

`k2`를 구하려면 **`y + (dt/2)·k1` 위치에서의 가속도**가 필요하다. 그 위치는
실제 우주선이 있는 곳이 아니라 **가상의 중간 지점**이다.

즉 **"임의의 위치를 넣으면 가속도를 돌려주는 순수 함수"** 가 있어야 한다.

```cpp
// 이런 형태여야 RK4가 가능하다
Vector2 ComputeAcceleration(const Vector2& pos, const Vector2& vel) const;
```

반면 `_force`에 힘을 누적해두는 방식(A-1)은 **"지금 이 순간의 힘"** 만 알고
있어서 중간 지점을 평가할 수 없다.

> 📌 **그래서 힘 계산을 "누적 버퍼"가 아니라 "함수"로 설계해야 한다.**
> 이건 RK4 때문에 억지로 맞추는 게 아니라, 애초에 **더 깨끗한 설계**다.
> 상태를 넣으면 결과가 나오는 순수 함수라 테스트하기도 쉽다.
>
> 💡 **추력처럼 "입력에 의존하는 힘"은 어떻게 할 것인가?**
> 한 물리 스텝 동안 입력이 고정이라고 보고 함수 안에서 참조하면 된다.
> **판단할 것:** 추력을 `ComputeAcceleration` 안에 넣을지, 스텝 밖에서
> 따로 더할지. 전자가 일관되지만 순수성이 조금 깨진다.

## A-6. 고정 타임스텝 — 적분기 비교의 전제조건

### 왜 가변 `dt`면 안 되는가

지금까지 `deltaTime`을 그대로 써왔다. 물리에서는 **이게 두 가지를 망친다.**

**① 재현성이 사라진다.** 같은 조작을 해도 프레임률에 따라 결과가 달라진다.
발사에 성공했다 실패했다 한다.

**② 적분기 비교가 무의미해진다.** 세 적분기를 비교하려면 **완전히 같은 조건**
이어야 하는데, `dt`가 매번 다르면 무엇 때문에 갈라졌는지 알 수 없다.

### 누산기(accumulator) 패턴

```
_accumulator += frameTime;

while (_accumulator >= FIXED_DT)
{
    PhysicsStep(FIXED_DT);      // 항상 같은 dt로만 적분
    _accumulator -= FIXED_DT;
}
```

프레임이 얼마나 걸리든 물리는 **항상 `FIXED_DT` 단위로만** 전진한다.
남는 시간은 다음 프레임으로 이월된다.

### ⚠️ 죽음의 나선 (spiral of death)

한 프레임이 아주 길어지면(디버거 정지, 창 드래그 등) `_accumulator`가 크게
쌓이고, `while`이 수십 번 돈다. 그러면 그 프레임이 더 길어지고, 누산기가 더
쌓이고... **영원히 못 빠져나온다.**

```
// 최대 스텝 수를 제한한다
int steps = 0;
while (_accumulator >= FIXED_DT && steps < MAX_STEPS)
{
    PhysicsStep(FIXED_DT);
    _accumulator -= FIXED_DT;
    ++steps;
}
if (steps >= MAX_STEPS) _accumulator = 0.f;   // 밀린 시간은 버린다
```

**"시간을 버린다"** 는 게 핵심이다. 시뮬레이션이 실시간보다 느려지는 것을
받아들이는 대신, 프리즈를 막는다.

> 💡 **판단할 것:** `FIXED_DT`를 얼마로?
> `1/60`이면 가볍고 `1/120`이면 정확하다. 궤도는 오차가 누적되는 계라
> `1/120`을 권하지만, **직접 두 값으로 궤도 드리프트를 측정해보고 정하는 게
> 이 주차의 좋은 실험이다.**

## A-7. 원궤도 속도 유도 — 검증의 기준선

### 왜 이 식이 필요한가

Part C의 핵심 테스트가 **"이 속도를 정확히 주면 완전한 원이 나오는가"** 다.
원궤도는 손으로 답을 낼 수 있는 몇 안 되는 경우라, **적분기와 중력이 동시에
맞았는지를 한 번에 검증**해준다.

### 유도

원운동을 유지하려면 **구심가속도 = 중력가속도**여야 한다.

```
구심가속도:  v² / r
중력가속도:  μ / r²

     v² / r = μ / r²
        v²  = μ / r
         v  = √(μ / r)
```

**끝이다.** 세 줄이면 나온다.

### 방향도 중요하다

크기가 맞아도 **방향이 반지름에 수직**이 아니면 원이 안 된다.

```
d = P_ship - P_planet           ← 행성에서 우주선으로
d̂ = d.Normalized()
수직방향 = (-d̂.y, d̂.x)          ← 90도 회전 (또는 (d̂.y, -d̂.x))

v = 수직방향 · √(μ / r)
```

> 💡 두 수직 방향 중 어느 쪽을 고르냐에 따라 **시계/반시계 공전**이 결정된다.
> 둘 다 유효한 원궤도다. 어느 쪽이든 원이 나와야 정상이다.

### 파생 — 탈출 속도

에너지 보존에서 바로 나온다. 무한히 멀어졌을 때 속도가 0이 되는 조건:

```
½v² - μ/r = 0
       v  = √(2μ / r)
```

**원궤도 속도의 `√2`배**다. 이 관계를 알아두면 게임 중에 "지금 속도면 탈출인가"
를 암산할 수 있다.

### 파생 — 역학적 에너지 (3주차 예고)

단위질량당 역학적 에너지:

```
E = ½v² - μ/r
```

| E | 궤도 모양 |
|---|---|
| `E < 0` | **타원** (속박 궤도) ← 승리 조건 |
| `E = 0` | 포물선 (딱 탈출) |
| `E > 0` | 쌍곡선 (탈출) |

> 📌 **이 값을 이번 주차부터 ImGui에 찍어두면 3주차가 훨씬 편하다.**
> 그리고 적분기 비교(A-5)의 측정값이 바로 이 `E`다. 한 번 만들어두면 두 번 쓴다.

## A-8. 발사 시퀀스와 중력 턴

### 왜 수직으로만 올라가면 안 되는가 ⭐

직관적으로는 "위로 계속 밀면 우주로 나가겠지"인데, **틀렸다.**

수직으로만 상승하면 궤도 속도(수평 방향)가 0이다. 엔진을 끄는 순간
**그대로 다시 떨어진다.** 아무리 높이 올라가도 마찬가지다.

> **궤도에 오른다는 건 "높이 올라가는 것"이 아니라 "옆으로 충분히 빠르게
> 가는 것"이다.** 뉴턴의 대포알 사고실험이 정확히 이 이야기다 —
> 충분히 빠르게 던지면 떨어지는 속도와 지면이 휘어지는 속도가 같아져
> 영원히 떨어지면서도 닿지 않는다.

### 중력 턴 (gravity turn)

실제 로켓의 발사 프로파일:

```
1. 수직 상승      — 대기가 두꺼운 저고도를 빠르게 벗어난다
2. 서서히 기울임  — 진행 방향을 수평 쪽으로 (중력 턴)
3. 거의 수평      — 궤도 속도를 벌어들인다
```

이름이 "중력 턴"인 이유: 실제 로켓은 살짝만 기울이면 **중력이 나머지를
알아서 돌려준다.** 기수를 계속 조종할 필요가 없다.

**이 게임에서는 플레이어가 `A`/`D`로 직접 기울인다.** 언제 얼마나 눕히느냐가
게임의 조작 재미이자 난이도가 된다.

> 📌 **이게 "게임이 성립하는 지점"이다.** 너무 일찍 눕히면 지면에 충돌하고,
> 너무 늦게 눕히면 연료/속도가 모자라 궤도에 못 든다. **중간이 정답인 구조라
> 게임이 된다.** 기획서의 "물리 조종 게임"이 여기서 실현된다.

### 발사 상태 머신

```
Idle (발사대 대기)
  │  발사 버튼
  ▼
Countdown (3·2·1)          ← TIME.AddTimer 사용
  │  카운트 종료
  ▼
Ascent (추력 조작 가능)
  │            │
  │ 지면 충돌   │ 궤도 진입 (3주차)
  ▼            ▼
Failed       Success
  │
  │ R 키
  ▼
Idle (상태 초기화)
```

**판단할 것:** 상태를 `enum` + `switch`로 둘지, `GameMode`에 위임할지.
엔진에 `GameMode`가 이미 있으니 **거기 두는 게 구조적으로 맞다**
(로드맵의 "게임 규칙은 GameMode" 원칙). 다만 우주선 상태와 밀접하니
`ASpaceship`에 두는 것도 실용적이다. **정한 이유를 주석으로 남길 것.**

### 지표면 충돌

```
if ((ship.pos - planet.pos).Length() < planet.bodyRadius)
    → 발사 실패
```

`Length()` 대신 `LengthSquared()`와 `bodyRadius²`를 비교하면 `sqrt`를 아낀다.
**다만 중력 계산에서 이미 `r`을 구했으므로 재사용하는 게 더 낫다** — 같은
프레임에 같은 거리를 두 번 구하지 않도록 설계할 것.

> ⚠️ **터널링 주의.** `dt`가 크고 속도가 빠르면 한 스텝에 지면을 **뚫고 지나가서**
> 다음 프레임엔 이미 행성 반대편에 있을 수 있다. 고정 타임스텝(A-6)이 이걸
> 크게 완화하지만, 완전히 막으려면 "이번 스텝의 시작점과 끝점을 잇는 선분이

## B-1. 물리 상태 + 가속도 함수 — 순수 함수로 설계 ⭐

**학습 근거:** A-1, A-2, A-5-8

가장 먼저 만들 것은 **상태**와 **가속도 함수**다.

```cpp
// 상태 — 이 둘만 저장한다
Vector2 _position;      // 월드 좌표 (AActor의 GetCenterPos()와 동기화)
Vector2 _velocity;

// ⭐ 임의의 상태를 넣으면 가속도를 반환하는 순수 함수

Vector2 ComputeAcceleration(const Vector2& pos, const Vector2& vel) const;
```

`SetCenterPos()`/`GetCenterPos()`를 쓴다. 1주차 B-7에서 이미 겪은 함정이다.

**판단할 것:** 물리 상태를 컴포넌트가 소유하고 액터에 동기화할까, 액터의
`_center`를 직접 읽고 쓸까? → **컴포넌트가 소유하고 스텝 끝에 한 번 동기화**
하는 쪽이 깔끔하다. 중간 계산이 액터에 새어나가지 않는다.

**✅ 검증:** `ComputeAcceleration`에 임의의 위치 두 개를 넣으면 **서로 다른**
가속도가 나온다 (같은 값이 나오면 위치를 안 쓰고 있는 것).

## B-2. 중력 — `a = μ·d / r³`

**학습 근거:** A-3, A-4

**함정 ①** — **방향 부호.** `d = 행성 - 우주선`이다. 뒤집으면 척력이 된다.
**이건 테스트 없이는 절대 못 잡는다.**

**함정 ②** — `r → 0` 처리. `r = max(r, bodyRadius)`로 클램프 (A-3).

**함정 ③** — 행성이 여러 개면 **전부 합산**한다. 하지만 **행성끼리는 중력을
주고받지 않는다** (로드맵: n-body 제외, kinematic 고정).

**판단할 것:** 모든 행성의 중력을 다 더할까, 가장 가까운 하나만 볼까?
→ 전부 더하는 게 물리적으로 옳고 계산량도 문제없다(9개). 다만 **멀리 있는
행성의 기여가 무시할 수준**이라 게임 느낌은 거의 같다. 전부 더하는 쪽을 권한다.

**✅ 검증 (⭐ 부호를 잡는 유일한 방법):**
1. 우주선을 행성 **위쪽**에 놓고 속도 0 → **아래로(행성 쪽으로)** 떨어지는가
2. 행성 **오른쪽**에 놓고 속도 0 → **왼쪽으로** 떨어지는가
3. ← 한 방향만 테스트하면 부호 실수를 못 잡는다 (1주차 표면 정렬과 같은 함정)

## B-3. 적분기 3종 + 런타임 토글 ⭐⭐

**학습 근거:** A-5 전부

**순서를 반드시 지킬 것: 반암시적 → 명시적 → RK4**

**왜 반암시적을 먼저 만드는가:** 나머지 작업(추력, 발사)이 안정적인 적분기
위에서 진행되어야 한다. 명시적 오일러로 시작하면 **모든 버그가 적분기 탓인지
로직 탓인지 구분이 안 된다.**

```cpp
enum class EIntegrator { SemiImplicitEuler, ExplicitEuler, RK4 };
```

### 3-1. 반암시적 오일러 (기본)
```
v += a(x)·dt
x += v·dt          ← 새 v를 쓴다
```

### 3-2. 명시적 오일러 (비교용)
```
x += v·dt          ← 옛 v를 쓴다
v += a(x_old)·dt   ← ⚠️ x를 갱신하기 전의 위치로 계산해야 한다
```

**함정** — 위치를 먼저 갱신해버리면 가속도를 새 위치에서 계산하게 되어
**의도치 않게 반암시적이 되어버린다.** 순서 차이를 보여주는 게 목적인데
차이가 안 나면 실험이 무의미하다. `a`를 먼저 구해두고 시작할 것.

### 3-3. RK4
```
k1 = f(y)
k2 = f(y + (dt/2)·k1)
k3 = f(y + (dt/2)·k2)
k4 = f(y + dt·k3)
y += (dt/6)·(k1 + 2k2 + 2k3 + k4)
```

**함정 ①** — 가중치가 `1:2:2:1`이고 나누는 값이 `6`이다. 합이 `6`이 되는지 확인.
**함정 ②** — `k2`/`k3`는 `dt/2`, `k4`는 `dt` 전체다. 여기가 자주 틀린다.
**함정 ③** — `f(y)`가 `(velocity, acceleration)` 쌍을 반환해야 한다.
위치의 변화율은 **속도**, 속도의 변화율은 **가속도**다. 이 대응을 헷갈리면
완전히 엉뚱한 결과가 나온다.

**판단할 것:** 상태 `(pos, vel)`과 미분 `(dPos, dVel)`을 담을 구조체를
만들 것인가? → 만드는 걸 권한다. 없으면 RK4 코드가 변수 8개로 뒤덮인다.

**✅ 검증:**
1. **반암시적으로 원궤도**를 돌렸을 때 궤도가 유지되는가 (C-2가 상세)
2. **명시적으로 같은 초기값** → 나선형으로 **바깥으로** 벗어나는가
   ← 안쪽으로 말리면 부호나 순서가 반대다
3. RK4가 반암시적보다 **눈에 띄게 원에 가까운가**
4. 세 적분기를 **런타임에 전환**해도 크래시 없이 이어지는가

## B-5. 추력 + 입력 ⭐ (Day 2에서 수행)

**학습 근거:** A-2, A-8

> 🔄 **원래 Day 5였으나 Day 2로 앞당겼다.** 중력을 넣는 순간 이걸 같이 고치지
> 않으면 실험이 성립하지 않기 때문이다. 아래 "차원" 절이 그 이유다.

이미 `ASpaceship::Input()`에 회전(`A`/`D`)과 이동(`W`)이 있다. **이동을
"위치 직접 변경"에서 "힘 추가"로 바꾸는 게 이번 작업이다.**

```
현재:  _pos += _forwardDir * _moveSpeed * dt      ← 물리를 무시하고 순간이동
변경:  a_thrust = _forwardDir * (thrust / mass)   ← 가속도로 작용
```

**차이가 결정적이다.** 전자는 키를 떼면 즉시 멈추지만, 후자는 **관성이 남는다.**
우주에서는 후자가 맞고, 이게 게임의 조작감을 만든다.

### ⭐ 왜 값 조정으로는 절대 해결되지 않는가 — 차원 문제

`_pos +=` 상태로 중력을 켜면 **우주선이 올라가다 반드시 떨어진다.**
그런데 `_moveSpeed`를 아무리 키워도 해결되지 않는다. 크기가 아니라
**차원(단위)이 다르기 때문이다.**

```
추력:  _moveSpeed = 100        [units/s]   ← 속도. 일정하다
중력:  g = 20                  [units/s²]  ← 가속도. 매초 20씩 누적된다
```

| 경과 | 중력이 만든 낙하 속도 | 알짜 |
|---|---|---|
| 0초 | 0 | ↑ 100 |
| 2.5초 | 50 | ↑ 50 |
| **5초** | **100** | **0 — 멈춘다** |
| 이후 | 100+ | ↓ 떨어진다 |

`_moveSpeed = 1000`으로 올리면 **50초 뒤에 지는 것뿐**이다.
**누적되는 쪽이 언제나 이긴다.** 유한한 값으로는 무한히 커지는 값을 못 이긴다.

추력을 가속도로 바꿔야 비로소 **같은 차원에서 겨루게 되고**, 그때부터
`TWR = a_thrust / g` 같은 크기 비교가 의미를 가진다.

> 🔑 **물리 값이 이상할 때 의심 순서: ① 차원 → ② 부호 → ③ 크기.**
> 대부분 ①이나 ②에서 잡힌다. **크기부터 만지는 게 제일 흔한 실수이고,
> 몇 시간을 태우는 지름길이다.**

**함정** — `ASpaceship`에 이미 있는 `_gravity = 9.8f` 멤버는 **지워야 한다.**
중력은 이제 `ComputeAcceleration`에서 μ로 계산된다. 두 군데서 중력을 주면
이중 적용된다 (트러블슈팅 P4와 같은 구조).

**판단할 것 ①** — 추력을 얼마로? → **TWR(추력대중량비)** 로 생각하면 감이 온다.
```
TWR = a_thrust / g_surface
TWR < 1  → 이륙 못 함
TWR ≈ 1.5~2.0 → 실제 로켓의 이륙 시점 범위
```
`g = 20`이니 `a_thrust = 30~40`이 출발점이다.

**판단할 것 ②** — 추력을 `ComputeAcceleration` 안에 넣을까, 밖에서 더할까?
→ 안에 넣으면 RK4가 추력까지 4차 정확도로 처리한다. 밖에서 더하면 순수성이
유지된다. **정답이 없으니 정하고 이유를 남길 것.**

**✅ 검증:**
1. `W`를 떼도 **관성으로 계속 나아가는가** (즉시 멈추면 아직 직접 이동 중)
2. 추력 없이 가만히 두면 행성으로 떨어지는가
3. TWR < 1로 설정하면 **이륙하지 못하는가** (물리가 맞다는 강한 증거)

## B-6. 발사 시퀀스 상태 머신

## B-8. 적분기 비교 하네스 ⭐ (포트폴리오 핵심 자료)

**학습 근거:** A-5 전부, A-7 (에너지 식)

**이게 2주차 최고의 산출물이다.** 반드시 만들고 자료를 남길 것.

### 무엇을 만드는가

같은 초기 조건에서 세 적분기를 **동시에** 돌리고, 궤적과 에너지를 비교한다.

```
초기 조건: 고도 300 원궤도 (v = √(μ/r) ≈ 124)
         → 진짜 답은 "완벽한 원"이므로 벗어남이 곧 오차다
```

### 측정할 것

| 지표 | 계산 | 의미 |
|---|---|---|
| 역학적 에너지 | `E = ½v² - μ/r` | **적분기 품질의 핵심 지표** |
| 궤도 반지름 | `r` | 원이면 일정해야 함 |
| 에너지 상대 오차 | `(E - E₀) / \|E₀\|` | 적분기별 비교에 적합 |

### 예상되는 결과

```
E 상대오차
   │      ╱ 명시적 오일러 (단조 증가 → 발산)
   │    ╱
   │  ╱
───┼────────────────── 반암시적 (0 근처 진동)
   │ ＼_ RK4 (아주 천천히 감소)
   └──────────────── t
```

> 📸 **이 그래프를 반드시 남길 것.** ImGui에 `PlotLines`가 있으니 실시간
> 그래프를 띄울 수 있고, 값을 CSV로 덤프해서 엑셀로 그려도 된다.
> **"한 줄 순서를 바꿨더니 발산하던 게 안정됐다"** 를 그림으로 보여주는 게
> 2주차 회고의 하이라이트다.

**판단할 것:** 세 적분기를 **동시에 세 개의 우주선으로** 돌릴까, **하나를
전환**하며 따로 측정할까?
→ 동시에 돌리면 한 화면에 세 궤적이 갈라지는 게 보여 **훨씬 강력한 그림**이 된다.
디버그 전용 모드로 만들어두면 게임 로직을 안 건드린다.

**✅ 검증:**
1. 세 궤적이 **처음엔 겹쳐 있다가 서서히 갈라지는가**
2. 명시적이 **바깥으로**, RK4가 아주 천천히 **안쪽으로** 가는가
3. `dt`를 절반으로 줄이면 RK4의 오차가 **약 1/16**이 되는가 (4차 정확도 확인)
   ← 이게 확인되면 RK4 구현이 진짜 맞은 것이다

# Part C. 자가 점검

> ⚠️ **반드시 이 순서대로.** 뒤 항목은 앞 항목이 맞다는 전제로 되어 있다.

## C-1. 자유낙하 — 해석해와 대조 (가장 먼저)

중력을 **상수**로 고정하고(`μ/r²` 대신 그냥 `g = 20` 아래 방향) 자유낙하시킨다.
등가속도 운동은 해석해가 있다:

```
v(t) = g·t
x(t) = x₀ + ½·g·t²
```

| # | 테스트 | 기대값 (`g = 20`) |
|---|---|---|
| 1 | 1초 후 속도 | `20` |
| 2 | 1초 후 낙하 거리 | `10` |
| 3 | 2초 후 낙하 거리 | `40` (4배 — `t²` 확인) |
| 4 | 우주선을 행성 **위**에 놓음 | **아래로** 떨어짐 |
| 5 | 우주선을 행성 **오른쪽**에 놓음 | **왼쪽으로** 떨어짐 |

> 📌 **1·2번이 적분기의 정확도를, 4·5번이 중력 방향 부호를 잡는다.**
> 반암시적 오일러는 `½g·t²`에 정확히 맞지 않고 약간 벗어난다 —
> **그게 정상이다.** `dt`를 줄이면 값이 수렴하는지를 보면 된다.

## C-2. 원궤도 — 물리 전체를 한 번에 검증 ⭐⭐

**이 테스트 하나가 중력 · 적분기 · 단위계를 동시에 검증한다.**

```
r = 1300 (고도 300)
v = √(μ/r) = √(2×10⁷ / 1300) ≈ 124.0
방향 = 반지름에 수직
```

| # | 테스트 | 기대값 |
|---|---|---|
| 6 | 반암시적으로 10바퀴 | `r`이 거의 일정 (몇 % 이내 진동) |
| 7 | 궤도 주기 | `≈ 66초` |
| 8 | 명시적으로 같은 조건 | **바깥으로 나선** |
| 9 | RK4로 같은 조건 | 가장 원에 가까움 |
| 10 | 속도를 `√2`배(≈175) | **탈출 — 돌아오지 않음** |
| 11 | 속도를 0.7배(≈87) | 타원 궤도 (근지점에서 지면 충돌 가능) |

> 💡 **6번이 통과하지 않으면 그 뒤는 전부 무의미하다.** 여기서 막히면
> C-1로 돌아가서 중력 방향과 크기를 먼저 확인할 것.
>
> ⚠️ **원이 아니라 타원이 나온다면**: 초기 속도의 **방향**이 반지름에
> 정확히 수직이 아닐 가능성이 크다. 크기(124)만 맞추고 방향을 대충 주면
> 타원이 된다.

# Part D. 회고 문서에 남길 것

1. **⭐ 적분기 3종 비교 그래프** — 같은 초기 조건에서 에너지가 어떻게 갈라지는지.
   **2주차 최고의 자료이자 면접 단골 주제다.** 궤적 스크린샷 + 에너지 그래프 둘 다.
2. **⭐ "한 줄 순서"의 위력** — 명시적 ↔ 반암시적의 코드 diff는 두 줄인데
   결과는 발산 vs 안정. **코드와 결과 그림을 나란히** 두면 강력하다.
3. **정확도 ≠ 보존성** — RK4가 4차 정확도인데도 장시간에서 에너지가 새는 것.
   "왜 게임 엔진들이 반암시적 오일러를 쓰는가"에 대한 답.
4. **질량이 상쇄되는 순간** (A-2) — `a = F/m`에 중력을 넣으면 우주선 질량이
   사라진다는 것. 그래서 `μ = GM` 하나로 묶은 설계 판단.
5. **단위계 설계** (A-4) — 실제 `G`를 못 쓰는 이유(float 정밀도)와
   "표면 중력에서 역산"한 과정. 게임 물리에서 항상 필요한 사고방식.
6. **고정 타임스텝** (A-6) — 왜 필요했는지(적분기 비교의 전제) + 죽음의 나선.
7. **중력 턴** (A-8) — "수직으로만 올라가면 궤도에 못 간다"를 실제로
   해보고 확인한 것. **실패 장면이 좋은 자료다.**

> 📸 **버그와 실패 장면이 자료다.** 명시적 오일러가 발산해 우주선이 화면
> 밖으로 날아가는 장면, 수직 상승 후 그대로 추락하는 장면 —
> **고치기 전에 먼저 찍어라.** 1주차에서 배운 교훈이다.

## 참고 — 막혔을 때 확인 순서

**물리는 "언제부터 틀렸는지"를 좁히는 게 핵심이다.**

1. **중력을 상수로 바꾸면 되는가?** (`μ/r²` → `g` 고정)
   → 되면 중력 계산(A-3) 문제. 부호·`r³`·클램프를 확인
2. **적분기를 반암시적으로 바꾸면 되는가?**
   → 되면 명시적/RK4 구현 문제
3. **`dt`를 10배 줄이면 되는가?**
   → 되면 적분 오차 문제 (알고리즘은 맞음). 고정 타임스텝을 확인
4. **추력을 끄면 되는가?**
   → 되면 추력 계산이나 `_gravity` 이중 적용 문제
5. **행성을 하나만 남기면 되는가?**
   → 되면 다중 행성 합산 문제
6. **값을 직접 찍어서** C-1 자유낙하 해석해와 대조
   → 여기서도 틀리면 가장 기본 단계가 문제다

> 💡 **1~2번을 먼저 하는 게 핵심이다.** 중력과 적분기 중 어느 쪽인지만
> 갈라도 탐색 범위가 절반이 된다. 물리 버그는 원인이 하나가 아닐 때가 많아서
> **"하나씩 정상으로 되돌리며 좁히는" 접근이 유일하게 통한다.**
