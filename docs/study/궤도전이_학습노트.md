# 궤도전이 학습노트 — 케플러 궤도 & 람베르트 문제

> "행성 간 자동 이동"(우주선 피킹 → 행성 버튼 → 자동 전이)을 만들기 위해 공부한 물리를 정리한다.
> 코드가 아니라 **개념과 수식** 위주. 실제 구현 코드는 `APlanet.cpp`, `Util.cpp`,
> `InterplanetaryTransfer.cpp`에 있다.

---

## 왜 필요했나

기존 우주선 궤도 계산(`OrbitalGameMode`)은 "지금 위치·속도로 어떤 궤도를 도는가"를 구하는
것까지였다. 행성 간 자동 이동을 만들려면 그 반대가 필요하다 — **"여기서 저기까지 이만큼
시간 안에 가려면 얼마나 빠르게, 어느 방향으로 출발해야 하는가."** 이걸 풀려면 먼저 행성들의
궤도 자체를 원이 아니라 실제 타원(케플러 궤도)으로 다뤄야 했다.

---

## 1. 케플러 궤도 — "궤도 요소 + 시간 → 위치"

### 왜 원운동으로는 안 되는가

원운동(`각도 += 각속도 × dt`)은 등속이라 계산이 쉽지만, 실제 행성은 **케플러 제2법칙**(같은
시간에 같은 넓이를 쓸어감)에 따라 근일점(태양에 가까울 때) 근처에서 빠르고 원일점에서
느리다. 등속 각도를 그대로 쓰면 **특정 시점에 행성이 궤도 위의 엉뚱한 자리**에 그려진다
(속도만 틀리는 게 아니라 위치 자체가 틀림).

### 핵심 기호

| 기호 | 이름 | 의미 |
|---|---|---|
| `a` | 장반경(semi-major axis) | 타원의 긴 반지름. 궤도의 "크기" |
| `e` | 이심률(eccentricity) | 0=원, 0~1=타원. 얼마나 찌그러졌는가 |
| `ω` | 근일점 편각(arg. of periapsis) | 타원이 어느 방향을 향하는지(회전 오프셋) |
| `n` | 평균각속도(mean motion) | "시간이 얼마나 빨리 흐르는가"에 해당하는 등속값 |
| `M` | 평균근점이각(mean anomaly) | `M = M0 + n·t` — **등속으로 흐르는 가짜 시계**. 실제 위치와 직접 대응 안 됨 |
| `E` | 이심근점이각(eccentric anomaly) | `M`(시간)과 실제 위치를 이어주는 다리. 케플러 방정식으로 구함 |
| `ν` | 진근점이각(true anomaly) | 태양에서 봤을 때 **실제** 각도. `E`로부터 계산 |
| `r` | 거리 | 그 순간 태양-행성 거리. `E`로부터 계산 |

### 케플러 방정식과 왜 반복법(뉴턴법)으로 푸는가

```
E = M + e·sin(E)
```

`E`가 방정식 양쪽에 있는데, 오른쪽 `E`는 `sin()` **안에 갇혀있다.** 이런 "변수가 삼각함수
안에 갇혀서 대수적으로 못 풀리는" 방정식을 **초월방정식**이라 부르고, 애초에 공식으로 풀리는
정답이 없다. 그래서:
1. `E ≈ M`으로 일단 찍는다
2. 그 값을 넣었을 때 방정식이 얼마나 안 맞는지(오차) 본다
3. 오차 방향으로 `E`를 조금 수정한다 (뉴턴법: 접선 기울기로 보정량 계산)
4. 2~3을 몇 번 반복하면 수렴한다 (이심률이 크지 않으면 5~6회로 충분)

### 위치·속도로 이어지는 흐름

```
M (시간에서 바로 계산) → [케플러 방정식, 반복법] → E → [삼각함수 공식] → ν, r → 위치
                                                    E → [속도 공식] → 속도
```

- 위치: `pos = 중심 + r·(cos(ν+ω), sin(ν+ω))`
- 궤도 "모양" 자체를 그릴 땐 시간이 필요 없으므로 `E`를 0~2π로 **직접 훑으면 됨**
  (케플러 방정식을 풀 필요가 없음 — 시간과 무관하게 궤도 형태는 고정이니까).

### 헷갈리기 쉬운 것 — "찌그러짐"과 "초점 오프셋"은 다른 값

이심률 `e`가 궤도에 만드는 시각적 효과는 두 가지인데, 크기가 완전히 다르다.

- **모양의 찌그러짐**(단반경/장반경 비율) = `sqrt(1-e²)` — `e=0.206`(수성)이어도 `97.86%`라
  거의 원처럼 보임. 육안으로 거의 안 티남.
- **초점(태양)이 타원 중심에서 벗어난 거리** = `a·e` — `e=0.206`이면 장반경의 `20.6%`나 벗어남.
  **이게 진짜 눈에 띄는 신호.**

→ "궤도가 알처럼 찌그러져 보여야 한다"는 기대는 틀렸고, "태양이 궤도 중심에서 한쪽으로
치우쳐 보인다"가 맞는 신호다. 실제 태양계도 이렇게 보인다.

### `μ`(중력변수) 없이 유도하기

케플러 3법칙 `n² = μ/a³`을 거꾸로 쓰면, 태양의 실제 중력변수를 안 넘겨받아도
`μ_effective = n²·a³`로 필요한 곳(속도·가속도 공식)에서 역산해낼 수 있다 — 이미 아는 값
(`n`, `a`)들 사이의 관계식으로, 모르는 값을 만들어내는 방식.

## 2. 람베르트 문제 — "위치 두 개 + 시간 → 속도"

케플러 방정식과 정확히 반대 방향의 문제다.

| | 입력 | 출력 |
|---|---|---|
| 케플러 방정식 | 궤도 요소(`a`,`e`) + 시간 | 위치 |
| 람베르트 문제 | 위치 **두 개**(`r1`,`r2`) + 걸리는 시간(TOF) | 속도(`v1`,`v2`) |

이 게임에서: `r1`=우주선 현재 위치, `r2`=목표 행성이 도착 시점에 있을 위치
(`GetFuturePos(TOF)`), 출력 `v1`=그 궤도를 타려면 **지금 가져야 할 속도**. 지금 실제 속도와
`v1`의 차이가 곧 burn(Δv).

### 왜 케플러 방정식보다 어려운가

케플러 방정식은 "이미 정해진 하나의 궤도" 위에서 위치를 구하는 문제였다. 람베르트 문제는
`r1`, `r2`를 지나는 궤도가 **무한히 많은 것 중에서**, 걸리는 시간이 정확히 `TOF`가 되는
**그 하나**를 찾아야 한다 — 미지수(`z`)를 하나 도입해서 그 무한한 후보들을 훑는 구조.

### 풀이 단계 (Universal Variable 방법)

**1단계 — 기하 정보**

| 기호 | 의미 |
|---|---|
| `r1n`, `r2n` | `r1`, `r2` 벡터의 크기(거리) |
| `Δν` (`dNu`) | 두 위치가 태양을 중심으로 벌어진 각도. 외적 부호로 진행 방향(반시계) 보정 |
| `A` | `r1n`,`r2n`,`Δν`로 만든 중간 계산값 (그 자체로 물리적 의미는 없음) |

**2단계 — Stumpff 함수 `C(z)`, `S(z)`**

궤도가 타원(`sin`/`cos` 필요)일지 쌍곡선(`sinh`/`cosh` 필요)일지 `z`값에 따라 갈리는데, 이
두 함수가 **그 둘을 하나의 식으로 통합**해준다. `z>0`이면 삼각함수처럼, `z<0`이면
쌍곡선함수처럼 동작하고, `z=0`에서 매끄럽게 이어짐.

**3단계 — `z` 찾기 (이분법)**

| 기호 | 의미 |
|---|---|
| `z` | 찾아야 할 미지수. 어떤 궤도를 고를지 정하는 "손잡이". `z>0`=타원, `z=0`=포물선, `z<0`=쌍곡선 |
| `y(z)` | `z`로부터 나오는 중간값. 음수면 그 `z`는 유효한 궤도가 아님 |
| `χ` (chi) | "보편 근점이각" — 케플러의 `E`를 타원/쌍곡선 모두 되게 일반화한 값 |
| `t(z)` | 이 `z`(=이 궤도)를 타면 걸리는 시간 |

`z`가 커질수록 `t(z)`도 커지는 단조 관계라, `t(z) == tof`가 될 때까지 `z`의 범위를 반씩
좁혀나간다(이분법). 이 프로젝트에서는 **최소 연료 전이만 찾을 것**이므로 `z ∈ [0, 4π²)`
(타원 궤도만)로 범위를 제한했다 — 쌍곡선(더 빠르지만 항상 더 비쌈)은 최소 연료 탐색에서
애초에 선택될 일이 없기 때문.

**4단계 — 라그랑주 계수로 속도 역산**

| 기호 | 의미 |
|---|---|
| `f`, `g`, `gDot` | 라그랑주 계수. 같은 궤도 위의 두 점(위치·속도)이 서로 무관하지 않고, 이 계수들로 연결됨을 이용 |

관계식 `r2 = f·r1 + g·v1`을 `v1`에 대해 풀면:
```
v1 = (r2 - f·r1) / g
```
`v2`도 짝을 이루는 공식(`v2 = (gDot·r2 - r1)/g`)으로 한 번에 나온다.

## 3. 실제 사용 흐름 (이 프로젝트에서)

1. 목표 행성을 고르면, 호만 전이 시간을 대략적인 중심값으로 잡고 그 주변 TOF 후보들을
   스캔한다(`FindBestTransfer`).
2. 각 TOF 후보마다: `목표 행성의 그 시점 위치`(`GetFuturePos`) 구함 → 람베르트 풀이 →
   필요한 Δv(`|v1-현재속도| + |v2-목표속도|`) 계산.
3. Δv가 제일 작은 TOF를 채택 — 이게 실제 미션 설계에서 쓰는 "포크찹 플롯" 탐색의 축소판.
4. (원래 "위상각 맞을 때까지 기다린다"는 계획이었는데, 람베르트로 넘어가면서 성격이
   바뀌었다 — TOF를 자유롭게 고를 수 있다는 게 람베르트의 특징이라, 정해진 위상각을
   수동으로 기다리는 대신 **"지금 당장 갈 수 있는 후보들 중 제일 싼 것"을 스캔하는 것 자체가
   대기를 대신한다.** 별도의 대기 로직을 안 만들어도 되는 이유.)

## 4. 실제 구현 — 파일별 정리

케플러 궤도(Step 1~2)에 이어서, 람베르트 계산과 그걸 실제 플레이에 연결하는 부분.

### `APlanet` — 미래 속도 추가
`GetFuturePos(t)`(기존)와 짝을 이루는 `GetFutureVelocity(t)`를 추가했다. 도착 시점에 목표
행성이 어떤 속도로 움직이고 있을지 알아야 두 번째 burn(도착 속도 맞추기)을 계산할 수 있어서.
`GetVelocity()`/`GetFutureVelocity()`가 내부적으로 같은 "E로부터 속도 계산" 함수
(`ComputeVelocityAtEccentricAnomaly`)를 공유하도록 리팩터링.

### `Util.h/.cpp` — 람베르트 솔버
`SolveLambert(r1, r2, tof, mu)` — Universal Variable 방법(위 2장 내용 그대로 코드로 옮김).
케플러 방정식 풀이(`SolveKeplerEquation`)랑 같은 파일에 둠 — 둘 다 "궤도역학에서 반복
계산이 필요한 범용 유틸리티"라는 성격이 같아서.

### `GameSystem/InterplanetaryTransfer.h/.cpp` — TOF 스캔 (신규 파일)
`FindBestTransfer(shipPos, shipVel, target, sunMu)` — 호만 전이 시간을 중심으로 TOF
후보 100개를 스캔하며 각각 람베르트를 풀고, 총 Δv가 제일 작은 후보를 `TransferPlan`으로
반환한다. 우주선/행성 상태만 받는 독립 함수라 `Util`보다는 전용 파일로 분리했다.

### `Widget_Main` — 행성 선택 버튼
`ShowPlanetButtons(planets)` / `HidePlanetButtons()` — 우주선을 피킹하면 화면 위쪽에
행성 버튼들이 동적으로 생기고, 다른 걸 클릭하면 사라진다. 버튼 클릭 시
`SetOnPlanetSelected` 콜백으로 어떤 행성이 선택됐는지 `MainWorld`에 알려준다.

### `MainWorld` — 연결
클릭 시 피킹된 게 우주선이면 버튼 표시(태양과 지금 있는 곳은 목록에서 제외), 버튼이
눌리면 `FindBestTransfer`를 호출해서 나온 `plan.v1`을 바로 `physics->SetVelocity()`로
적용 — 지금은 burn을 "즉시 반영"하는 방식(기존 `KEY_0`/`KEY_1` 디버그 순간이동과 같은 결).
