# FirstOrbit — 기술 회고

> 포트폴리오/이력서 첨부용으로 프로젝트 전체를 정리한 문서.
> 주차별 상세 트러블슈팅은 `docs/study/1주차_troubleShooting.md` ~ `3주차_troubleShooting.md`에
> 따로 있고, 이 문서는 그중 핵심만 추려 "무엇을, 왜, 어떻게" 관점으로 재구성했다.

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 제목 | FirstOrbit (궤도 진입) |
| 장르 | 2D 물리 시뮬레이션 / 조종 게임 |
| 플랫폼 | Windows (WinAPI, GDI 렌더링) |
| 개발 환경 | C++ · 외부 엔진·물리 라이브러리 미사용 (자체 프레임워크) |
| 개발 기간 | 약 3주, 1인 개발 |
| 핵심 기술 | 행렬 기반 뷰 변환 · 수치 적분 · 만유인력 · 궤도역학 · 절차적 조명/렌즈효과 |

**한 줄 소개** — 지표면에서 우주선을 발사해 대기권을 뚫고, 스케일을 넘나드는 카메라로 우주를
드러낸 뒤, 중력을 이용해 안정 궤도에 진입하고 나아가 행성 간 이동과 블랙홀까지 다루는 물리
기반 조종 게임.

**핵심 컨셉** — *"발사할 때 나를 끌어내리던 중력이, 궤도에 나가면 나를 공전시키는 도구가
된다."* 지상에서는 극복해야 할 적이던 중력이, 궤도에서는 이용해야 할 자원으로 바뀌는 인식의
전환이 이 게임의 학습 목표이자 재미다.

## 2. 왜 엔진 없이 WinAPI/GDI인가

물리 라이브러리·렌더 엔진을 쓰지 않은 건 "그게 없어서"가 아니라 **증명하려는 대상이 물리
그 자체**였기 때문이다. 벡터·행렬·수치적분·만유인력·보존법칙을 라이브러리 뒤에 숨기지 않고
직접 구현해서, "왜 이렇게 만들었는가"를 코드 레벨에서 설명할 수 있게 하는 것이 목표였다.
렌더링도 같은 이유로 스프라이트 파이프라인 대신 대부분을 GDI 도형(원·선·픽셀)과 직접 만든
픽셀 버퍼 조작으로 그렸다.

## 3. 핵심 기술 4축

### 3.1 행렬 기반 카메라 — 하나의 뷰가 스케일을 넘나든다

`Screen = T(half) · S(zoom) · R(θ) · T(-pos)` 3×3 동차좌표 행렬 하나로 뷰 변환·줌·회전을
전부 처리한다. 지표면 근접 샷과 태양계 전체 조망이 **별도 화면 전환이 아니라 같은 평면을
다른 배율로 보는 것**이라는 게 설계의 핵심 — 지면이 곡률 때문에 지평선처럼 보이다가, 줌아웃할
수록 원으로 휘며 궤도 탑뷰가 된다. 클릭 피킹도 `View`의 역행렬로 화면 좌표를 월드로 되돌려
판정한다.

- **아핀 전용 역행렬**과 **일반 3×3 역행렬(여인수 전개)**을 둘 다 구현해서 상호 검산 — "왜
  아핀 전용이면 충분한가"를 코드로 증명.
- 카메라 위치 보간은 선형(Lerp), 줌은 로그 스케일 지수감쇠 — 사람이 체감하는 거리/배율
  감각이 선형이 아니라 로그적이기 때문. 회전은 `LerpAngle`로 최단 경로만 돈다
  (`atan2(sin(Δ), cos(Δ))`로 접어서 350°→10°가 -340°로 도는 걸 방지).

### 3.2 수치 적분 3종 비교 — 이 프로젝트의 물리 실력 증명 구간

명시적 오일러 / 반암시적(semi-implicit) 오일러 / RK4를 런타임에 전환 가능하게 구현하고,
같은 초기 조건에서 궤도가 어떻게 갈라지는지 비교했다.

```
① 명시적 오일러      x += v*dt;  v += a*dt;   // 위치 먼저 — 에너지가 새어나가 궤도가 발산
② 반암시적 오일러     v += a*dt;  x += v*dt;   // 속도 먼저 — 심플렉틱, 에너지 보존 → 채택
③ RK4                k1~k4 가중평균            // 4차 정확도, 국소적으로는 더 정확
```

**반암시적 오일러를 기본으로 채택한 이유**: RK4가 한 스텝 안에서는 더 정확하지만, 장기간
누적되는 에너지 드리프트는 반암시적 오일러(심플렉틱 적분기)가 더 안정적이다. 궤도 게임처럼
"몇 분간 안정적으로 도는가"가 중요한 상황에선 국소 정확도보다 장기 안정성이 우선이라는 판단.
고정 타임스텝(`FIXED_DT=1/240`) + 누적기(accumulator) 패턴으로 프레임 속도와 물리를 분리했다.

### 3.3 만유인력 + 조석력 보정 — 수학적으로 유도한 안정화

`F = G·M·m/r²`를 우주선에만 적용하고 행성끼리는 서로 당기지 않는 n-body 배제 설계로
시뮬레이션 붕괴를 방지했다(로드맵에서 "시간이 남아도 안 넣는다"고 명시한 유일한 항목).

지구가 실제로 공전을 시작하면서 우주선이 지구를 놓치고 이탈하는 문제가 생겼는데, 원인을
숫자로 확인했다 — 지구가 자기 궤도를 유지하는 구심가속도(`a_earth=24`)가 지구 근처에서
우주선이 받는 지구 중력(`a_local≈11.8`)보다 **두 배 컸다.** 현실에서는 태양이 지구도 당기고
근처 우주선도 거의 동일하게 당겨서 상쇄되는데, 이 프로젝트는 태양 중력을 시뮬레이션하지
않으므로 그 상쇄가 빠져 있었던 것. 지구가 받는 것과 같은 가속도를 우주선에도 보정으로
더해주는 방식으로 해결했고, 상대좌표(`ρ = ship.pos - home.pos`)로 놓고 보면 이 보정이
`d²ρ/dt² = g_earth(ship)`로 **지구의 움직임 자체를 수식에서 완전히 소거**한다는 걸
직접 유도해서 확인했다.

### 3.4 궤도역학 — 판정과 예측

비에너지(`ε = v²/2 - μ/r`)와 비각운동량(`h = r×v`)으로 장반경·이심률을 구하고, 근지점
`a(1-e)`/원지점 `a(1+e)`으로 승리 조건을 판정한다. 예측 궤도선은 현재 상태를 값으로만
복제해(`{pos, vel}` 구조체 — 액터를 통째로 복사하면 컴포넌트 포인터가 이중 해제된다) 앞으로
N스텝을 미리 적분해서 점선으로 그린다.

## 4. 원래 계획을 넘어선 확장 구현

3주 로드맵의 MVP(발사 → 궤도 진입 클리어)를 완성한 뒤, 시간이 남아 원래 스코프 밖이던
기능들을 추가로 구현했다.

- **연료 시스템** — 추력 사용에 비례해 소모, HUD 게이지 표시, 리필 기능.
- **대기권 연출** — 레일리 산란 상대 계수(`β∝1/λ⁴`, R:G:B ≈ 0.27:0.61:1.0)에 대기 밀도
  감쇠(`e^(-h/H)`)를 곱해 하늘색을 팔레트로 고르지 않고 **공식에서 유도**. 같은 밀도 값으로
  별의 밝기와 카메라 줌까지 동시에 구동해, "고도 하나가 세 가지를 동시에 구동한다"는 원래
  설계 의도를 그대로 구현.
- **SOI(영향권) 기반 행성 간 이동** — 원래 로드맵에서 "게임 하나를 더 만드는 규모"라며
  제외했던 항목. 라플라스 SOI 공식(`r_SOI = a·(μ_planet/μ_parent)^0.4`)으로 각 행성의
  영향권을 계산하고, 매 프레임 현재 위치가 어느 SOI 안인지 판정해 중력원을 자동 전환한다.
  경계에서 판정이 매 프레임 튀는 걸 막기 위해 현재 타겟에만 5% 히스테리시스를 둔 것도
  포인트.
- **블랙홀** — 실제 중력체(SOI 시스템과 충돌하지 않도록 `Planet`과 별개 타입으로 설계) +
  절차적 렌더링: 배경 별을 방사형으로 왜곡시키는 중력렌즈 효과, 강착원반 글로우, 이벤트
  호라이즌(검은 코어), 블랙홀 주위를 공전하며 서서히 빨려드는 별 무리(가까울수록 빠르게
  도는 각운동량 보존 흉내). 전부 텍스처 없이 픽셀 버퍼 직접 조작 + 프리멀티플라이 알파
  그라디언트로 구현.

## 5. 엔지니어링 하이라이트 — 인상적인 디버깅 사례

전체 트러블슈팅은 50개가 넘지만, 그중 방법론이나 판단 근거 자체가 회고감인 것들만 추렸다.

### 5.1 프레임타임 의존 버그를 파이썬 시뮬레이션 + Debug/Release 비교로 확정

지구가 공전을 시작한 뒤, 조석력 보정(3.3절)까지 다 넣었는데도 시간이 지나면 우주선이 지구를
놓쳤다. 코드만 봐서는 원인을 못 찾아서, **게임과 똑같은 물리 공식을 파이썬으로 그대로
재현**해 시뮬레이션했더니 이론적으로는 안정적이었다(상대거리 1298~1300 유지). "그럼 코드가
아니라 실행 환경 문제"라는 가설을 세우고 Release 빌드로 테스트하니 정상, Debug 빌드에서만
이탈하는 걸 확인했다.

근본 원인: `UPhysicsComponent`의 물리 서브스텝 상한(`MAX_STEPS=5`)이 한 프레임에 소화할 수
있는 시간(`5×1/240≈0.0208초`)이, 프레임 델타타임 클램프(`GMaxDeltaTime=0.1초`)보다 5배
작았다. Debug 빌드처럼 프레임이 느려지면 지구(캡 없음)는 그 델타타임을 전부 소화하는데
우주선 물리는 5스텝만 처리하고 나머지를 버려서, 지구와 우주선의 "시간"이 어긋나며 조석력
상쇄의 전제(같은 시간만큼 같이 전진)가 깨졌다. `MAX_STEPS`를 25로 올려 해결.

> 코드 리딩만으로는 잡기 어려운, 실행 환경(빌드 구성·프레임 속도)에 의존하는 버그를
> **재현 가능한 실험(파이썬 재구현 + A/B 빌드 비교)**으로 좁혀나간 사례.

### 5.2 같은 종류의 "그리는 순서" 버그가 블랙홀 렌더링에서 3번 연속 다른 모습으로 재발

블랙홀 강착원반 글로우를 추가했는데 완성 화면에 아무것도 안 보였다. 좌표 검증용 마젠타 원을
DIB 파이프라인과 무관하게 순수 GDI로 그려서 "좌표 계산은 맞다"를 먼저 증명한 뒤, 원인이
**그리는 순서**라는 걸 확인했다 — 글로우를 그린 직후, 왜곡 루프가 그 자리를 다른 곳에서
샘플링해온 값으로 덮어쓰고 있었다.

순서를 뒤집으니(왜곡 → 글로우) 이번엔 글로우가 이벤트 호라이즌(검은 코어) 자리를 덮어써서
검은 원이 사라졌다. 다시 순서를 정리해 **① 배경 왜곡 → ② 글로우 → ③ 검은 코어를 맨 마지막에
다시 뚫기** 3단계로 확정. 이후 블랙홀 주위를 도는 별 무리를 추가했을 때도 **같은 패턴의
버그가 세 번째로 재발**했다(별을 왜곡 루프보다 먼저 그려서 지워짐) — 처음 두 번의 경험 덕분에
원인을 훨씬 빠르게 짚어 같은 3단계 순서 안에 편입시켰다.

> 한 번 고친 버그의 **패턴**을 기억해두면, 같은 원인이 다른 대상(글로우 → 별)에서
> 재발했을 때 진단 속도가 확연히 빨라진다는 걸 실제로 겪은 사례.

### 5.3 "복붙한 숫자"가 스케일이 다른 곳에서 반복적으로 문제를 일으킴

- 별 배경(1주차): 20만 개를 범위 ±300만에 뿌렸더니, 화면에 실제로 들어오는 건 전체의
  0.04%뿐이라 20만 번 순회해서 100개 남짓만 그리는 낭비 구조. 스케일(가장 먼 행성 기준)에
  맞게 범위를 줄이니 더 가벼우면서 더 잘 보였다.
- `LaunchWorld` 별(3주차): `MainWorld`(태양계 스케일)에서 쓰던 범위를 그대로 복붙해서
  발사 장면(수백~수천 단위 스케일)에서는 별이 거의 안 보임.
- 블랙홀 주위 별(3주차): 회전 반경(`maxRadius`)을 좁히려다 이벤트 호라이즌 반지름보다
  작게 잡아버려서, 별들이 전부 검은 코어 안쪽에 갇혀 안 보이는 버그.

세 번 다 "다른 스케일에서 쓰던 숫자를 그대로 가져다 씀"이라는 같은 실수였다. 매직 넘버를
발견할 때마다 "이 값이 왜 이 크기인가"를 먼저 확인하는 습관, 그리고 서로 연동돼야 하는
값(핸드오프 고도 vs 하늘색 정규화 기준 등)은 이름 있는 상수 하나로 통일해 어긋날 여지를
없앤 것이 이후 재발을 줄였다.

### 5.4 설계 전제가 깨졌을 때 절반쯤 만든 기능을 폐기한 판단

1주차 로드맵은 "둥근 행성 표면 어디서 발사해도 지평선이 수평으로 보이게" 하는 표면 정렬
회전을 필수 항목으로 잡고 있었다. 실제로 구현에 착수해 검증 UI까지 만든 뒤에야, 이 게임의
실제 흐름(평면 바닥에서 발사 → 화면 전환 → 태양계에서 궤도 진입)에서는 발사 구간이 애초에
평면이라 지평선이 기울어질 일 자체가 없다는 걸 깨달았다. 표면 정렬 코드는 전량 삭제하고
발사 월드와 우주 월드를 별도 `World`로 분리하는 쪽으로 설계를 바꿨다.

> 문서의 작업 항목을 순서대로 따라가는 것과, 그 항목이 지금 만들려는 것에 실제로 필요한지
> 되묻는 것은 별개라는 걸 코드를 절반쯤 만든 뒤에 배웠다. 버린 시간은 있었지만, 그 과정에서
> 만든 범용 기능(각도 최단경로 보간 등)은 그대로 재사용됐다.

### 5.5 GDI 리소스 성능/정합성 이슈 — 회전 렌더링을 도입했다가 되돌린 사례

행성 텍스처가 전부 미리 라이팅되어 있어 공전해도 하이라이트가 화면상 고정 방향을 향하는
문제를 고치려고 `RenderRotated`(회전 블릿)를 행성 9개에 적용했더니 fps가 10까지 떨어졌다.
원인은 회전 렌더링이 호출마다 `CreateCompatibleDC`/`CreateCompatibleBitmap`으로 임시 버퍼를
새로 만들고 지우는 구조였기 때문 — 캐싱으로 최적화했지만, 캐시 버퍼 크기 계산에서 "이번
호출에 필요한 크기"와 "캐시된 실제 버퍼 크기"를 섞어 쓰는 버그가 새로 생겨 화면이 깨졌다.
최종적으로는 **성능 대비 이득이 크지 않다고 판단해 회전 렌더링 자체를 롤백**하고, 이미
있던 실시간 그림자(`ApplyPlanetShadow`)로 낮/밤 표현을 대신했다.

> 기능을 "구현해서 붙이는 것"과 "붙일 가치가 있는지 성능으로 검증하는 것"은 별개다.
> 되돌리기로 한 결정도, 그 판단 근거(fps 수치)와 함께 남겨두면 회고 자료가 된다.

## 6. 이 프로젝트로 증명한 것

- **선형대수를 실전에 옮김**: 동차좌표 행렬 하나로 뷰 변환·줌·회전·역변환 피킹까지 처리.
- **수치해석의 트레이드오프를 이해하고 근거 있게 선택함**: 3종 적분기를 직접 비교해
  안정성 vs 정확도 트레이드오프를 근거로 반암시적 오일러를 택함.
- **고전역학을 코드로 검증함**: 조석력 상쇄를 수식으로 유도하고, 그 유도가 맞는지 실제
  빌드로 검증함.
- **환경 의존적 버그를 재현 가능한 실험으로 좁히는 디버깅 방법론**: 코드 리딩만으로 안 될 때
  외부 시뮬레이션·A/B 빌드 비교로 전환하는 판단력.
- **엔진 없이 절차적 렌더링을 직접 구현함**: 프리멀티플라이 알파 글로우, 픽셀 단위 중력렌즈
  왜곡, 레일리 산란 기반 하늘색 등을 라이브러리 없이 GDI 픽셀 조작만으로 구현.
- **스코프를 판단하는 능력**: 넣을 것(SOI, 블랙홀)과 뺄 것(n-body, 표면 정렬, 행성 회전
  렌더링)을 근거를 가지고 결정하고, 필요하면 이미 만든 것도 되돌림.
